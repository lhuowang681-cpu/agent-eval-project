# Agent 源码改进归因与开发榜规范

## 1. 报表目标

本 Skill 的默认受众是负责 Agent 编排源码的开发人员。默认首页不是全链路故障榜，而是 **Agent 源码可改进问题榜**：回答“在外部条件不变的情况下，修改哪个 Agent 内部模块可以避免或显著缓解该 Badcase”。

工具来源先做硬分流：`builtin` 才允许进入 Agent 源码责任判断；`mcp`、`plugin`、`unknown` 一律按外部原因处理，不进入开发榜。以下事实本身不足以认定 Agent 源码存在问题：

- MCP、第三方 Tool、Provider 或外部网关返回 Error；
- 用户明确指定的工具、表名、参数或外部资源不可用；
- 账号权限、凭证绑定、套餐、Quota、环境开通存在问题；
- 外部服务超时、限流、断连、返回 5xx 或非 JSON；
- Trace 中仅出现 `ToolExecutionError`，但缺少有效输入与失败阶段证据。

## 2. 强制双结论

每条候选问题必须分别输出：

1. `direct_failure_cause`：本次 Trace 直接失败的表面机制，可以是外部故障；
2. `agent_source_issue`：有证据支持的 Agent 内部源码问题；若未发现，必须明确写“未发现有证据支持的 Agent 源码问题”。

同时记录：

- `error_exposure_node`：错误最终在哪里暴露；
- `abnormal_input_source`：异常输入或错误决策从哪里产生；
- `first_internal_abnormal_node_id`：最早的 Agent 内部异常节点；
- `source_module_id`：固定归因树上的 Agent 源码责任模块；
- `source_issue_category`：该模块下具体的问题机制；
- `counterfactual_fix`：只修改该 Agent 模块、保持外部条件不变时，问题是否可避免或显著缓解；
- `internal_evidence_node_ids`：支持内部源码归因的证据节点；
- `actionability`、`confidence` 与 `needs_review`。

## 3. 开发榜硬准入门禁

只有同时满足以下条件，问题才允许进入开发 Top 5、开发模块分布和代表 Case：

1. `actionability = agent_source_actionable`；
2. 存在 `first_internal_abnormal_node_id` 或可审计的“推断内部根因节点”；
3. 存在至少一条 `internal_evidence_node_ids`；
4. `source_module_id` 属于固定 8 层 56 模块；
5. `counterfactual_fix` 给出明确的反事实判断；
6. 证据足以区分“外部故障”和“Agent 对外部故障的处理缺陷”；
7. 非仅由错误关键词、工具名或最后抛错节点推断。

不满足门禁时分流：

- `external_dependency`：外部 MCP、Tool、Provider、网关、数据库或第三方服务故障；
- `user_or_business_input`：用户明确指定的工具、表名、参数、权限或业务前提导致失败；
- `non_code_configuration`：凭证、Quota、套餐、环境开通和人工配置；
- `attribution_governance`：证据不足、节点链缺失、仅有通用错误；
- `potential_agent_improvement`：可能存在内部改进机会，但证据未达到正式开发榜门槛。

外部问题不是简单降低一个数值权重，而是先从开发榜硬分流。只有通过门禁的内部问题才计算开发优先级。

## 4. 工具错误的责任拆分

对于 Tool/MCP/Provider 错误，必须依次判断：

1. 工具是用户明确指定，还是 Agent 自主选择？
2. 错误参数来自用户、Agent 生成、Context/RAG/Memory、前序 Tool Result，还是 Runtime 转换？
3. Assistant 发出的参数与工具实际接收的参数是否一致？
4. Tool Call 输入是否满足 Schema、语义和环境要求？
5. Agent 是否已获得正确的元数据或工具结果，但没有采用？
6. 外部错误发生后，Agent 是否存在独立可证明的状态误判、结果漏回填、无限重试、错误重试、无熔断、无降级或提前结束？

归因规则：

- 调用前参数、SQL、工具选择、上下文或 Payload 已错误：归产生异常数据的 L2/L4/L5/L7 模块；
- Tool Call 输入有效，工具自身执行、路由或响应解析失败：直接故障可归 L6 或外部依赖，但不自动进入 Agent 源码开发榜；
- 外部工具失败后 Agent 错误处理：拆成“外部直接故障”和“Agent 内部处理缺陷”两个问题，开发榜只统计后者；
- 用户明确提供错误参数且 Agent 仅忠实执行：默认归 `user_or_business_input`；只有产品契约明确要求预检且 Trace 证明预检缺失，才另立内部问题；
- 只有通用 `ToolExecutionError`：归 `attribution_governance`，不得默认归 L6 或 L2.2。

## 5. 归因树作为一级类别

开发报表采用两级分类：

- 一级类别：`source_module_id + module_name`，必须来自 8 层 56 模块；
- 二级类别：`source_issue_category`，描述该模块内的具体代码机制。

Top 5 默认按“一级模块 → 二级问题”的去重 Topic 数排列。模块图只统计通过开发榜门禁的问题。

不得为了类别丰富而强行分散模块；但 L2.2 不得作为兜底桶。以下问题应优先检查对应模块：

- Tool Schema、工具清单或可用性错误 → L4.6；
- Skill 未注入或激活结果未回填 → L4.7；
- Tool Result 未写回、执行指令顺序错误 → L2.5；
- Tool Call/Result 消息顺序或结构变形 → L4.5；
- Provider Payload、Tool Use/Result 配对错误 → L5.4；
- Tool Arguments 流式拼接错误 → L5.5；
- Provider 参数类型、采样或 Thinking 转换错误 → L5.2/L5.7；
- State、Pending Tool、Resume 丢失 → L3.1；
- 结束事件、流事件重复或缺失 → L3.2/L3.3；
- 子任务完成后主 Agent 未恢复 → L7.4；
- 上下文注入重复、缺失或超限 → L4.3/L4.4/L4.5；
- 证据不足 → L8.3，仅进入归因治理页。

## 6. 模块级 Top 5 查重与开发优先级

开发 Top 5 的一级统计单位是固定归因树 `module_id`，不是未经查重的二级问题类别。必须按以下顺序执行：

1. 按 `module_id` 聚合；
2. 在每个模块内部，从多个二级问题中选择一项开发价值最高的代表问题；
3. 每个模块最多进入 Top 5 一项；
4. 再对不同模块的代表问题排序，选出模块级 Top 5；
5. 未查重的原始二级问题频率榜只放审计附录，用于说明哪些问题因同模块重复而未进入首页。

因此，当 L2.2 存在多个高频二级问题，而 L4.5、L5.4、L5.7、L6.1 也有有效问题时，Top 5 应优先呈现五个不同的模块代表项，而不是被五条 L2.2 占满。

模块内和跨模块排序不能只看频率，统一采用：`开发优先分 = 源码可解决性×45% + 内部证据完整度×30% + 用户影响×15% + 去重 Topic 频率×10%`。四个维度均归一化到 0–100，模块源码可解决性先验必须覆盖固定 8 层 56 模块，以 `development_priority.py` 为唯一配置源。应按以下优先级综合判断：

1. **Agent 源码可改进性**：上下文窗口、Payload 构造、参数转换、状态/事件、结果回填等明确可修改内部源码的问题大幅提权；
2. **证据完整度**：能定位内部异常节点、字段和值变化、预期行为与反事实修复的问题提权；
3. **开发资源必要性**：必须投入 Agent 开发资源才能修复的问题提权；
4. **用户影响**：硬失败高于质量下降、性能下降和已恢复问题；
5. **去重受影响 Topic 数**：频率提供温和增益，但不能覆盖前述开发价值；
6. **外部性和信息缺失惩罚**：Tool/MCP/SQL、用户电脑环境、用户指定工具、输入来源无法还原的问题显著降权，优先进入附录。

外部工具问题即使高频，也不能压过低频但明确可修改 Agent 源码的问题。例如“上下文构造超过模型窗口”“Provider Payload 非法”“Thinking 参数转换错误”应显著高于缺少工具、SQL 或用户环境来源信息的失败。

## 7. Case 固定展示字段

每个开发代表 Case 至少展示：

- 归因树一级模块；
- 模块下二级问题；
- 外部/直接故障现象；
- 错误暴露节点；
- 参数或异常输入来源；
- 最早内部异常节点；
- Agent 源码问题；
- 反事实修复判断；
- 纳入开发榜依据；
- 内部证据节点；
- 外部依赖因素；
- 最终影响状态；
- 修复建议与建议核验的源码范围。

如果未发现内部问题，Case 必须明确标记“不进入开发榜”，不得为了凑满 Top 5 强行映射到 Agent 模块。

## 8. 模块多样性质量审计

模块多样性是完整归因的结果，不是配额目标。每批报告仍必须输出：

- 候选问题类别数；
- 通过门禁的内部问题类别数；
- 实际命中的一级模块数和层数；
- L2.2 占内部问题比例；
- L6/外部错误被分流的比例；
- L8.3 与待复核比例；
- 各阶段过滤数量及原因。

出现以下情况必须触发人工复核：

- 内部问题只命中 1–2 个模块；
- L2.2 占比异常高；
- 大量 Tool/MCP Error 没有输入来源分析；
- Top 5 中包含无内部证据的外部故障；
- 为凑模块多样性而使用低置信度归因。

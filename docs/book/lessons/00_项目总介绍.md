# 这个项目做什么，怎样向面试官介绍

## 先用一句话认识它

这是一个面向 Agent 开发人员的轨迹评测与故障归因方向：把一次任务执行中留下的模型调用、工具调用、返回结果和状态变化整理起来，找出失败的直接原因以及有证据支持的内部改进点，再形成可回查的报告，帮助开发人员决定先修什么。

这里有两个系统：一个是执行用户任务的 Agent 平台，一个是分析执行记录的归因工具。我们重点学习和准备新增的是第二个；理解第一个，是为了知道记录从哪里来、错误怎样产生和传播。

## 它解决的实际麻烦是什么

假设一个企业助手可以查订单、搜索资料、调用数据库。用户只看到一句“查询失败”，开发人员却可能面对几十条消息、几次模型调用和多次重试。最后一个错误是工具返回“日期格式不对”，但真正的问题可能早在此前已经出现：模型生成了错误格式、运行时转换坏了参数，或者用户明确提供了不符合要求的输入。

如果直接统计所有 Error，会遇到三个工程问题。第一，同一个任务重试三次，报表看起来像发生了三次独立业务失败。第二，服务宕机、用户权限不足和内部代码错误混在一起，开发人员拿到一份无法直接行动的清单。第三，报告只写“编排模块有问题”，却不提供参数、节点和判断过程，别人无法复核。

因此，归因工具不能只给错误起名字。它要逐步回答：这是真失败还是日志里提到失败？是哪次调用？当时发出什么、收到什么？最早在哪里偏离预期？改内部哪个机制能改善什么？证据够不够？影响了多少个不同任务？

## 从用户请求到开发报告，一次走完

用一条贯穿案例说明。用户输入“查询 2026-10-23 的订单”。工具要求参数是明确日期，但 Agent 发出了 `date="今天"`，工具拒绝；Agent 又原样调用一次，最终告诉用户失败。这个例子是教学构造，用来理解流程。

1. **Agent 平台执行任务。** 它组织上下文、调用模型、拿到工具调用意图、执行工具并处理结果。这里真的发生业务动作。
2. **观测系统保存轨迹。** 记录请求、工具参数、错误正文、调用 ID、父节点关系、时间等。记录越完整，之后越容易分清问题来源。
3. **数据适配器统一格式。** 不同导出的字段名可能不同，把原始 ID、消息和调用关系整理为分析器理解的结构，同时保留原始记录位置。
4. **失败检测器提取异常事件。** 工具明确返回失败，才形成对应事件；用户说“请处理 error 日志”不应被当成执行失败。
5. **归因步骤形成候选判断。** 检查要求是否可见、参数由谁产生、工具实际收到什么、后续怎样处理。直接原因是格式拒绝，内部问题候选是参数生成或校验缺陷；重复调用可能是另一项治理问题。
6. **证据与责任审核决定去向。** 引用的节点必须存在，内容应支持判断，证据缺失时进入复核。来源合同里的严格要求与旧脚本的启发式实现并不完全一致，这是后续个人增量的切入点。
7. **统计和报告服务开发决策。** 按任务去重，分别展示事件数和任务数；对达到要求的问题排序，附代表案例、证据和修复建议。

这七步是职责地图。参考包中有不同入口和多轮报表脚本，不能因此认定它们已经在当前机器统一运行。后续自己的小工具会选择一条清楚的离线路径，把合同和验收真正串起来。

## 技术不是清单，每一项都要回答“用来做什么”

| 所在层 | 参考材料里的技术 | 承担什么工作 | 学习重点 |
|---|---|---|---|
| 被测平台 | TypeScript、Agent Runtime、服务端执行器 | 组织决策、执行指令、回填结果和推进状态 | 一次请求怎样执行和终止 |
| 平台数据与调度 | PostgreSQL、Redis、队列与事件 | 业务持久记录、运行态、协调和下一步调度 | 权威数据、临时状态与异步边界 |
| 观测来源 | Langfuse Trace / Observation、导出文件 | 保存模型和工具等运行记录，供拉取或离线分析 | 观测粒度、字段完整度与身份关联 |
| 归因处理 | Python、JSON / JSONL、规则与正则 | 适配输入、识别明确失败、整理候选结果 | 可复现处理、错误分流与数据合同 |
| 可选模型分析 | OpenAI 兼容接口、固定 taxonomy、结构化 JSON | 辅助理解较复杂的轨迹语义与责任候选 | 输出还要经过枚举、证据和语义检查 |
| 统计与选样 | pandas、NumPy、本地 TF-IDF / 余弦距离 | 分组、计数、分值计算及一种代表样例选择 | 去重单位、公式目的和选择偏差 |
| 交付展示 | CSV、Excel、HTML、图表和审计表 | 让开发人员查看问题分布、代表 Case 与证据 | 能否回到原始事实，而非样式细节 |

Excel 报表生成文件还会使用相关工作簿处理库；旧 requirements 文件没有完整覆盖所有脚本的依赖，不能据它声称整个包一键安装可跑。对现在的学习，先掌握上表各层的职责，不需要先掌握全部库的 API。

模型归因与确定性规则是两条不同路线。模型路线能够表达更复杂的语义判断，但需要接口、成本管理和输出审核；规则路线更可复现，适合明确失败字段和有限合同，也更容易漏掉未覆盖场景。参考收敛算法里的 TF-IDF 是本地文本表示，用于挑代表 Case，不等于训练了归因模型，也不是已经接入了外部 Embedding。

## 这类项目最值得讲的工程设计

**数据合同先于算法。** 如果任务 ID 缺失、调用和结果配错，后面的模型再强也可能分析错对象。保存原始输入和关联规则，是让结果可信的基础。

**直接故障与内部责任分开。** 外部工具返回 500，可以是外部问题；Agent 在明确预算后仍反复调用，则可能另有内部处理缺陷。修重试不能让外部服务恢复，但能减少等待和额外成本。

**结论先过证据门禁，再谈优先级。** 高频率不能弥补不存在的证据节点。分数回答治理顺序，证据回答结论能否成立。

**保留不确定。** 只有一个通用错误、缺少参数来源时，输出待复核比编造模块更有用。与此同时也要报告覆盖率，避免所有案例都弃权却宣称系统表现好。

**先小闭环，再扩展。** 自己的首轮工具从合成 JSONL 走到有证据回链的 JSON / Markdown 报告。此时文件已经能承载输入、结果和复现实验；等有真实模型或多用户需求，再决定接入模型与存储。

## 面试时可以怎样介绍这个方向

下面这段用于说明项目内容，不代表已经完成个人开发：

“这个方向关注 Agent 的运行可靠性。一个任务往往有多轮模型和工具调用，只看最后的错误，容易把外部服务失败误归给内部代码，也容易把一次任务的重试重复统计。归因工具会读取运行轨迹，关联调用与结果，识别明确失败，分析最早可见的内部异常，并把判断绑定到具体证据节点。最后按不同任务去重，结合可解决性、证据和影响形成开发报告。参考实现主要使用 Python、Langfuse 导出、规则和可选的大模型分类，配合 pandas 统计和 Excel / HTML 展示。学习重点是证据审核、责任边界和统计口径。后续个人实现先做确定性的离线闭环，再验证是否需要模型。”

如果面试官接着问“你本人做了什么”，当前应明确说明：上游平台和参考脚本来自已有资料，现在在学习分析；自己的离线闭环尚未开发。等增量完成后，再用“我新增了什么、哪个反例揭示问题、修改前后实际结果怎样”替换计划部分。项目概述和个人贡献是两种不同问题，都要回答清楚。

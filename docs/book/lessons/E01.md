# 一次失败怎样变成一份开发报告

## 先理解业务，再认识模块

我们从一个能查订单的助手开始。普通用户只希望输入日期，得到订单；开发人员关心的则多一层：如果没有查到，是没有订单、参数不合法、权限不够，还是系统处理出了错？这些情况对用户都可能表现为“没查出来”，处理方式却完全不同。

这个项目的主线，是帮助开发人员把一次模糊的“失败”整理成可以核对的判断。它不负责替用户查订单，而是读取查订单过程留下的记录，说明发生了什么、哪些内部机制值得检查、证据够不够。

把“做业务”和“分析业务执行过程”分开，会让后面的学习更容易。执行系统需要模型、工具和状态；分析系统需要轨迹、身份关联、判定合同和报告。二者相连，但不是同一套职责。

## 这里的 Agent 到底是什么

在这个例子中，Agent 是围绕任务反复做决定并调用能力的程序。用户的一句话进入模型之前，系统会准备上下文和可用工具说明。模型可以返回普通文字，也可以提出工具调用；真正访问工具的是执行程序。工具结果进入上下文后，模型再决定继续调用还是给最终回答。

因此，一个任务可能是“用户请求 → 模型决定查订单 → 工具返回 → 模型解释结果”，也可能在失败后多走几轮。模型是决策环节的重要组成部分，但保存消息、执行请求、限制重试、检查审批和更新状态，仍由工程代码承担。理解这点，就不会把系统里的每个错误都称为“模型不够聪明”。

## 先看一条完整的失败故事

下面是一份教学案例。假设用户明确要求查询 `2026-10-23`，工具合同规定 `date` 必须是 `YYYY-MM-DD` 格式。合同就是调用双方约定的字段、类型和合法取值要求；例如 `date` 是日期字符串，而不是任意自然语言。

| 顺序 | 节点 | 角色与内容 | 它告诉我们什么 |
|---|---|---|---|
| 1 | n1 | 用户：查询 2026-10-23 的订单 | 目标日期由用户明确给出 |
| 2 | n2 | 上下文：工具要求 date 为 YYYY-MM-DD | 该次决策可见的格式要求 |
| 3 | n3 | Agent 生成调用 c1，参数 date="今天" | 发出的输入已偏离要求 |
| 4 | n4 | 工具收到 c1，返回 success=false，提示日期无效 | 第一次明确执行失败 |
| 5 | n5 | Agent 生成新调用 c2，仍传 date="今天" | 同样问题没有被纠正 |
| 6 | n6 | 工具返回 c2 失败 | 第二次失败事件 |
| 7 | n7 | Agent 最终回复无法查询 | 任务以失败告终 |

这些节点属于同一个教学任务 task-A 和一条 Trace trace-A。Trace 可以先理解为把这一段运行过程连在一起的观测记录；节点是记录中的具体消息或动作。工具调用 ID c1 / c2 用来关联“发出的调用”和“对应结果”，它们与节点 ID 的职责不同。

这里已经能读出两个关键事实。首先，工具并不是凭空失败，它收到了不符合格式的参数。其次，用户给出的日期是明确的，而 n3 发成了“今天”。但我们仍不能跳过参数传递细节：如果只记录了模型输出和工具报错，没有记录实际接收参数，就还需要排查中间转换有没有改动。教学表明确写出收到 c1 的参数，是为了让这条因果链成立。

## 第一段工程：平台怎样留下可分析的记录

执行平台需要记录的不只是最终回答。至少应该知道用户原请求、当时使用的工具合同、发出的参数、实际返回、调用身份与状态变化。有时间和父子关系，还可以重建先后与关联。

为什么要保留调用 ID？假设同时查订单和天气，两次工具返回顺序与发出顺序不同。如果只按“上一条 assistant、下一条 tool”配对，很容易把天气结果配给订单请求。身份关联能表达“这个返回属于 c1”，而不依赖它恰好出现在相邻位置。

为什么要保留原始记录？分析过程会清理长文本、统一字段和筛选样本。如果只保留清理后的摘要，后来发现判断有争议，就无法核对是否删掉了关键输入。原始记录是复核依据，摘要是便于处理的视图，两者职责不同。

## 第二段工程：适配器整理数据，但不替归因下结论

观测数据可能来自 JSON、JSONL 或工作簿。同一个字段可能叫 `id`、`trace_id` 或 `effective_trace_id`。适配器的工作，是把来源对象映射为后续模块理解的结构，并说明映射规则。

可以把规范后的数据理解成三张相互关联的小表：任务表记录“用户要完成什么”；轨迹表记录“本次执行是哪一段”；节点表记录“各步发生什么”。如果来源没有可靠任务 ID，就应标明未知或使用明确的回退规则，不能为了让表好看而凭空补出真实任务身份。

在订单例子中，适配器把 n3 与 n4 用 c1 关联，把 n5 与 n6 用 c2 关联，并保留 task-A / trace-A。此时还不应该输出“GeneralChatAgent 有 bug”。它只证明数据已经整理成可以分析的形式。

## 第三段工程：先识别失败，再分析责任

失败检测问的是“哪次动作明确失败”。n4 和 n6 都有 `success=false`，因此形成两个工具失败事件。n2 的工具说明即使写着“非法日期会返回 error”，也只是说明文字，不是已经发生的错误。

责任判断再往前追：工具的拒绝是直接失败机制，n4 是第一次暴露位置；在这份完整案例里，n3 是当前可见最早偏离要求的内部调用节点。n1、n2、n3、n4 合起来，支持“明确目标和格式要求已经提供，但实际发出不合格参数”这一候选结论。

这里的“最早”是证据可见范围内的最早，不等于已经查明每个底层模块的最终责任。参数可能在模型决策、上下文组织、参数转换等环节产生偏差。要归到固定源码模块，还需要对应输入输出和路径证据。先提出可核对的候选，再决定能否确认，会比直接贴标签更可靠。

反事实修复用于检查建议是否真的针对机制：保持工具及日期规则不变，如果在发起请求前按已知合同处理日期，就能避免本案例中的格式拒绝。另一个可能改进是遇到相同拒绝后不再原样重复调用。前者改善输入正确性，后者减少无效重复，两项建议解决的后果不同。

## 第四段工程：报告应该写成什么样

下面就是这条教学轨迹能形成的报告内容。它把已见事实与待确认部分分开，而不是写一段无法核查的“智能根因总结”。

| 报告字段 | 本例的合理内容 |
|---|---|
| 用户目标 | 查询 2026-10-23 订单 |
| 直接失败原因 | 工具因日期参数格式不合法拒绝调用 |
| 错误暴露位置 | n4、n6 |
| 最早可见异常 | n3 发出 date="今天" |
| 支持节点 | n1 的明确目标、n2 的格式要求、n3 的参数、n4 的实际拒绝 |
| 内部问题候选 | 参数生成 / 校验未满足可见合同，具体责任模块待核对 |
| 另一项治理候选 | n5 原样重试，没有纠正已知错误 |
| 反事实建议 | 校验并修正日期可避免本例格式拒绝；限制无效重试可减少额外开销 |
| 数量 | 2 次失败事件，1 条 Trace，1 个受影响任务 |

为什么最后一行不能写“两个用户受影响”？因为 c1 和 c2 是同一个任务的两次失败调用。开发人员需要同时了解系统噪声量和业务影响面，两个数都保留，比只选一个更有用。

## 把案例改一下，结论就应该改变

如果 n3 发出合法日期，而工具返回服务 500，直接原因就变成外部服务故障。没有内部错误处理证据时，不能继续沿用“内部参数生成有问题”。如果此后又违反明确的最多三次调用预算，仍然反复调用，则可以另立内部预算治理问题。这个判断不需要否认外部故障。

如果缺少 n1、n2，只剩 n4 的“非法参数”，我们只能确认被拒绝，尚不能证明参数是 Agent 自主生成、要求当时可见，也不能确认应改哪个模块。此时进入待复核是合理结果。真实工程里的重要能力之一，就是知道哪些问题目前答不出来。

## 学完这一节，你已经得到什么

你已经看到一条完整链：执行任务留下记录，适配数据建立关联，检测明确失败，分析最早异常与直接原因，审核证据，按任务去重，最后形成开发报告。E02 才会继续拆开平台内部如何决策和执行；本节不要求你先会数据库或读完 TypeScript。

一句可以直接理解的项目概括是：这个工具把 Agent 的运行记录变成有证据的失败分析，帮助开发人员区分外部问题和内部改进点，并避免重复调用夸大受影响任务数。后面的设计，都是为了让这句话在真实数据上成立。

# Agent 怎样决策、执行和推进状态

## 为什么不能只把它想成一次模型问答

普通问答可以是“输入给模型 → 得到文字”。Agent 任务多了工具和后续决策：模型提出查订单，程序真的调用订单工具，把结果交回模型，模型再决定怎样回答。程序还要处理失败、等待审批、用户取消和运行预算。一次模型返回只是整个过程中的一步。

继续使用上一节订单案例。平台第一步看到用户请求，安排模型生成；模型返回一个工具调用意图后，平台第二步执行工具；工具返回后，第三步再让模型解释结果。这里的“第几步”是教学上的执行边界，实际 stepCount 如何计数由运行时规则决定。

## 先认识三种数据

**State 是当前运行状态。** 它保存继续执行需要的信息，例如消息、步数、花费、待处理工具和当前运行状态。它回答“现在处于什么情况”。

**Context 是当前这一步的情境。** 例如当前 phase 是收到用户输入、收到模型结果，还是工具批次完成。phase 帮助决策程序理解“刚发生的是什么类型的事”。Context 与 State 有联系，但不能简单当作相同对象。

**Instruction 是下一步要做的动作。** 例如 call_llm、call_tool、请求人工审批或 finish。指令描述动作，执行器才产生真正的网络请求或数据库写入。这样，“决定调用”和“调用已经完成”就能被明确区分。

## Brain、Runtime、Executor 各负责什么

Brain 可以先理解为决策器。参考平台的 GeneralChatAgent 根据 phase 和状态决定指令：用户输入后安排模型；模型结果中有工具调用时检查是否需要人工介入；工具完成后再安排模型；不再需要调用时结束。决策器也有工程分支，并非所有控制都由大模型自由决定。

Runtime 是运行引擎。参考实现的一次 step 会复制当前状态、递增步数、构造或接收情境、取得指令、选择执行器、收集事件，并返回新状态与下一步情境。一次可以有多个指令，执行到需要阻塞的状态时会停止本轮继续推进。

Executor 是实际干活的适配层。模型执行器组织请求并调用模型；工具执行器处理工具调用；服务端可以注入自己的执行器以连接数据库和业务服务。参考 Runtime 的执行器注册允许配置覆盖默认实现，Agent 自带执行器的优先级更高。这解释了为什么相同运行引擎可以用于不同执行环境。

## 顺着一次成功调用走

| 时刻 | 输入是什么 | 发生什么 | 输出给谁 |
|---|---|---|---|
| 用户输入到达 | 请求、已有状态 | Brain 选择调用模型 | Runtime 得到 call_llm 指令 |
| 模型执行 | 消息与工具说明 | 模型返回工具名、参数和调用 ID | 形成新的结果情境 |
| 工具准备 | 模型结果、审批策略 | Brain 判断立即执行还是等待 | 执行指令或等待状态 |
| 工具执行 | 工具指令 | Executor 发起实际调用 | 返回值、事件与新状态 |
| 结果处理 | 工具结果已回填 | Brain 安排模型继续处理 | 生成最终回答或下一次调用 |
| 任务结束 | 模型给出结束结果 | 平台保存结束状态与事件 | 用户和观测系统 |

重点是“回填”。订单工具返回十条订单，如果结果没有被写入下一轮可见的消息或状态，模型可能仍然认为没有查到。工具调用成功只能证明工具阶段成功，不能证明整个任务成功。归因时就要对照“工具已返回”和“后续模型实际看见了什么”。

## 状态、事件与存储为何都存在

状态是一张当前快照，例如“正在等待工具”。事件是一串已发生的事实，例如“发起 c1”“c1 返回”“进入下一步”。只有当前状态，不容易解释怎样走到这里；只有事件，也可能需要重建才能知道现在该怎样继续。

平台服务层协调状态保存、消息持久化、事件和下一步安排。参考服务端路径借助 Redis 保存运行信息和协调，业务记录使用数据库模型。队列帮助把下一步安排成一个后续执行，而不是让所有工作都依附当前 HTTP 请求一直等待。客户端也可以在本地循环推进；两种路径不应混作一种部署形态。

保存状态不等于自动获得完美恢复。例如工具已执行成功、结果还没保存就崩溃，恢复程序可能不知道是否应再次执行。此处需要明确副作用身份、保存顺序和重试合同。本书在这一节先建立问题意识，不把参考平台未验证的恢复保证当成事实。

## 为什么要这样拆，代价又是什么

拆分后可以用固定的模型结果测试决策，用假的执行器测试状态推进，或替换客户端 / 服务端执行器，而不用每次都连真实工具。错误也更容易定位到“决策错、转换错、执行失败、结果漏回填”中的某一段。

代价是接口和状态传递变多，消息身份、字段转换和持久化时机都可能出错。工程设计不是组件越多越好，而是这些边界能否帮助验证和定位问题。首个个人离线归因器没有执行业务副作用，可以采用更简单的文件流水线，无须照搬整个平台的运行架构。

## 用三个失败对照巩固

发错参数属于决策输入或参数生成链上的候选问题；合法参数遇外部 500 属于执行阶段直接失败；工具返回成功却没有进入下一轮上下文，则可能是结果回填问题。三者都可能最终显示“查询失败”，但修复位置和证据需求不同。

现在你可以这样理解运行时：它把当前状态和本步情境交给决策器，拿到指令，交给执行器执行，再将结果和事件变成下一次决策的依据。状态、身份和终止规则把多次调用连成一个任务。

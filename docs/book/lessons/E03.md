# 循环、取消和审批为什么需要工程治理

## 一个看起来正常的循环怎样变成故障

假设模型每次看到工具失败，都再次提出相同调用。只要平台的规则是“还有 tool_calls 就继续”，循环就可能一直推进。业务任务没有更接近完成，模型和工具调用却不断增加，费用和等待时间持续累积。

因此，是否继续运行不能完全依赖模型愿不愿意结束。工程侧需要步数、成本、等待和取消等约束。本节使用参考原版 / 修订版中的机制说明设计目的；涉及具体运行效果，仍需实验验证。

## 软收敛和硬停止各解决什么

参考 Runtime 在超过最大步数后可以设置 forceFinish，让后续进入收敛流程；服务端还加入默认步数预算与额外硬闸。软收敛的目的，是尽量让模型有机会总结已有结果，给用户一个能读懂的结束说明；硬闸则处理模型仍不配合、流程没有收敛的情况。

例如设教学预算为三步，第三步时系统要求不再继续工具规划并尽快结束，随后仍要留出处理已返回结果、形成最终消息的空间。这个例子说明机制，不是原服务的真实默认配置。参考修订服务默认 maxSteps 是 1000，硬闸余量为 5，不能把教学数字当成源码常量。

两层限制的取舍在于：仅硬停容易把用户留在没有解释的中间状态；仅请求模型收尾又不能保证停止。成本预算是另一个维度，因为一次步骤也可能很贵。步数、成本和单次调用超时需要分别定义，不能用一个参数替代所有治理。

## 为什么“取消接口成功”后还可能继续运行

先看一个典型的丢失更新过程。执行中的 Worker 先读到旧状态 status=running，用户随后点击取消，取消处理把状态改为 interrupted；Worker 完成工具调用后，把自己手中的整份旧状态写回，running 又覆盖了 interrupted。

| 时间 | 执行方 | 存储中的结果 |
|---|---|---|
| t1 | Worker 读取 running 快照 | running |
| t2 | 取消处理写入 interrupted | interrupted |
| t3 | Worker 写回持有的旧快照 | running，取消信号丢失 |

参考修订版增加独立的持久化中断标记，使取消信号不依赖容易被整份状态覆盖的同一个字段，并维护运行中的 runtime，以便向活动执行传播中断意图。设计上的关键是：取消属于控制信号，不应悄悄被普通业务状态保存冲掉。

这还不等于所有工具都能立即停。发出取消、平台确认收到、停止安排下一步、当前网络调用真正中止，是四个不同时间点。验证要分别观察它们；外部工具如果不支持取消，可能只能阻止后续动作，而无法撤销已发生的副作用。

## 审批为什么不能只相信前端传来的说明

工具 manifest 可以理解为工具说明与策略信息，其中可能包含人工介入要求。平台执行工具时需要知道具体策略。如果调用方漏传 manifest，而执行路径仍能找到工具并执行，就会出现“执行能力存在，但审批依据缺失”的脱节。

参考修订版在服务端根据实际启用工具补齐相应 manifest，并在部分判断中区分“工具说明存在但没有审批要求”和“整份工具说明缺失”。前者可能是已知不需审批，后者是平台缺少判断依据，不能一概默认放行。

审批本身还包含恢复流程：进入等待 → 用户做出决定 → 关联待审批调用 → 恢复恰当步骤。只测试“弹出了审批”是不完整的；还应测试批准后能继续、拒绝后不会执行、重复批准不会重复造成副作用等条件。它们是应设计的验收场景，不表示本轮已测试。

## 怎样把设计变化变成验证结论

先固定版本和输入。分别准备持续返回工具调用的模型替身、正在执行的慢工具、缺少 manifest 的请求，再比较原版 / 修订版对应的行为。记录步数、终止原因、取消时刻、后续调用以及待审批状态，而不只看返回码。

模型替身适合验证循环和状态分支，因为输出可控；它不能证明真实模型任务质量。历史报告可以帮助选择复现目标，真正的“修复有效”需要当前同条件实验结果。

理解这一节后，原版与修订版的对照就不再只是找不同。你能说出每处变化针对哪一种失效机制、采取了什么控制、可能付出什么代价，以及还需要哪类实验补齐证据。

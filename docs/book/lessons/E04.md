# 数据怎样进入分析器，离线到底指什么

## 先把输入输出说清楚

一条归因流程最先面对的是文件或接口，不是根因。观测系统中的记录可能通过接口拉取，也可能被导出为 JSONL 或工作簿。JSONL 是一行一个 JSON 对象的文本形式，适合逐行处理；工作簿则可能把节点、错误和轨迹信息拆在不同 Sheet 中。

输入适配器负责回答：一行代表什么？哪些字段标识 Trace？消息藏在哪一层？错误正文是否被截断？遇到坏行是整批停止还是记录后继续？这些决定会影响之后的覆盖率和计数，所以需要显式合同。

## 参考包中有两条重要路线

旧主入口的大致顺序是“拉取或读缓存 → 可选从工作簿补充去噪轨迹 → 模型分类 → 聚合 → 图表和 Case”。其中数据获取与模型归因是不同步骤。offline 主要控制不再拉取远端数据，skip_classify 才控制使用已有分类结果。

结构化 JSONL 入口则读取导出分片中的消息和 Provider 输出，关联工具调用，按明确失败信号与规则形成分类行，再输出不同范围的结果表。它不等于把旧模型流程换了一种文件后缀，二者的字段、分类策略和证据要求均需分别核对。

| 路线 | 输入依赖 | 核心判断 | 主要限制 |
|---|---|---|---|
| 缓存 / 拉取加模型分类 | Trace 摘要，可能补充节点 | 固定分类树下的模型候选 | 摘要截断、模型错误、接口与成本 |
| 结构化 JSONL 规则 | messages、调用 ID、真实返回与 output | 明确失败形式和有限规则 | 未覆盖形式、来源启发式、责任证据可能不足 |

选哪条路线应由目标决定。首个个人闭环选择合成 JSONL，是因为可以固定输入、人工核对期望，又无需先恢复企业服务。它证明的是工程合同，不自动证明模型归因能力。

## “离线”要拆成三个开关理解

第一个开关是数据从哪里来：远端观测接口还是本地文件。第二个开关是分析怎样完成：本地规则还是外部模型。第三个是结果保存到哪里：本地报告还是远端服务。

因此，“从本地读数据，再发给模型分类”仍有网络调用；“不调用模型，但实时拉取 Trace”也不是全离线。只有输入、分析和输出都不依赖网络，才能按这份合同说是完整离线。本项目首轮个人工具将明确采用这个含义。

## 一份输入接收单应该长什么样

设本轮收到 100 行教学数据，其中 2 行不是合法 JSON，3 条没有节点 ID，10 条没有真实 Session。合理的接收报告应分别写明：总行数、成功解析数、坏行位置、哪些记录可继续分析，以及不同字段的缺失数。

不能静默丢掉 2 行，再让后面的报告宣称“覆盖全部 100 条”；也不能把缺失 Session 补成 Trace ID 后继续称它为真实 Session。回退值可以服务处理，但回退事实必须随结果保留。此处数字只是演示数据合同，不是已有运行成绩。

## 为什么新工具不直接 import 所有旧脚本

Python 文件的顶层语句会在导入时执行。参考脚本有加载环境、创建目录和读取必需环境变量等行为，入口名本身不能证明导入无副作用。复用前先分离纯数据处理与外部依赖，才容易做真正离线的验收。

最小边界可以是：适配器只读明确指定的文件，分析器只接收规范对象，报告器只写明确的输出目录。以后接 Langfuse 或模型时，用独立适配层替换对应环节，保持中间合同稳定。这是用小闭环降低依赖复杂度的工程目的。

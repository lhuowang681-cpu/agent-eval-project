# 怎样确认一次工具调用真的失败

## 失败检测是一道事实筛选

用户说“帮我解释 error handling”，这句话包含 error，却没有任何执行失败；工具返回 success=true，并附带错误处理说明，也不等于调用失败。若只正则搜索全部文本，正常消息、引用和说明都会混入报错统计。

所以首先限定观察对象：真实工具返回或明确的模型 / Provider 错误输出。再解释该对象的状态合同。这样，系统先证明发生了什么，再讨论为什么发生。

## 调用与返回先配对

设 Agent 同时发出订单调用 c1 和天气调用 c2，天气先返回，订单后返回。通过 tool_call_id，可以把 c2 的成功归给天气、c1 的失败归给订单。如果仅按相邻位置配对，分析器可能认为订单成功、天气失败，之后所有责任分析都偏离事实。

正常关联至少保留调用 ID、工具名、发出参数、结果和原始位置。找不到对应调用的失败结果，可以保留“孤立失败返回”，但参数来源应标缺失，不应从工具名猜出原输入。

## 结构化失败怎样判定

参考检测器会展开可解析的返回内容，检查 success / ok 为 false、is_error 为 true、status 为 failed 等形式，也接受部分明确文本前缀和非零退出码。例如 `status=failed` 能表达状态，`[exit code: 2]` 能表达命令异常结束。

| 返回 | 可以确认的内容 | 还不能确认的内容 |
|---|---|---|
| success=true，说明文字含 error | 未匹配失败状态 | 整个用户任务是否完成 |
| success=false，message=invalid date | 当前调用报告失败 | 日期是谁生成、哪段代码负责 |
| 明确非零退出码 | 命令执行未正常结束 | 是否由参数、环境或依赖造成 |
| 模糊文字，没有明确状态 | 需要其他合同或复核 | 不能因没匹配失败就确认成功 |

这是两个容易混淆的层次：检测器没有发现失败信号，是“未检出”，不一定是“成功”。成功也应有合同，例如明确成功状态和满足预期的输出。参考恢复代理的局限，就与这一区别有关。

## 检测成功之后怎样分类

参考规则路径会识别工具来源：builtin、MCP、plugin 或 unknown。来源说明工具怎样接入，不直接说明事故责任。builtin 仍可能遇外部服务故障；MCP 失败后，Agent 仍可能存在独立的错误重试。

旧脚本根据工具名称匹配来源，并采用特定报表的外部分流规则。这适合解释“当前入口会怎么处理”，却不能升级成所有平台通用的责任定律。新合同若允许外部故障和内部治理并存，应单独定义两个结论与各自证据。

## 一个完整的检测输出

对于订单调用 c1，检测层可以输出：属于 trace-A；工具为 order.query；调用参数日期为“今天”；返回明确 success=false；失败证据来自 n4 的状态与错误正文；调用来源判断为某种类型并注明依据。

检测层暂时不必写“编排模块故障”。把事件与事实保存完整，会让归因层有机会比较 n1 的用户输入、n2 的工具要求和 n3 的参数。若检测时就把原始内容压成一句标签，后续判断反而失去依据。

## 怎样验证这一步

用四类对照数据检查：正常返回含 error 字样、真正结构化失败、明确退出码失败、无明确状态的返回。再加入并行乱序、找不到调用和重复采集。预期要分别定义“确认失败、确认成功、证据不足”，而非把所有输入硬分成成功 / 失败。这就是失败检测的工程价值：让后面的归因从可靠事实开始。

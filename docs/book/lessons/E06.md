# 同一个任务报错三次，应该怎样统计

## 先定义业务目标，再定义计数

用户一次要求“查询订单”，这是一个可验收目标。为完成它，系统可能生成多条 Trace，每条 Trace 里又可能有多个工具调用。一次调用失败形成事件；用户随后提出天气查询，则可能是同一会话中的另一个任务。

所以四个对象的用途不同：事件衡量异常动作，Trace 衡量观测记录，任务衡量业务目标，Session 衡量会话关系。它们之间需要身份映射，不能仅靠字段名互换。

## 用一张账本算清楚

设 task-A 是订单查询：trace-1 中 c1、c2 分别失败；恢复执行后 trace-2 中 c3 失败。用户在同一 Session 又提出 task-B，trace-3 中 c4 失败。假设四次调用身份明确，没有重复采集。

| 范围 | 失败事件 | Trace | 不同任务 | Session |
|---|---|---|---|---|
| 只有 task-A | 3 | 2 | 1 | 1 |
| task-A 与 task-B 合计 | 4 | 3 | 2 | 1 |

这四个数分别有用。排查无效重试时需要看到三次事件；描述多少个目标被影响时应看一个任务。若把事件数直接当任务数，会让重试多的模块显得影响面特别大。

## 去重其实有两层

第一层是采集去重。同一个 c1 的失败返回被导出两遍，通常仍然是一件事，应该根据稳定身份合并，且保留重复来源或冲突说明。第二层是影响去重。c1 和 c2 是真正发生的不同调用，应保留为两次事件，但同属于 task-A，影响任务数只加一次。

用“工具名加错误文本”作为唯一键可能误合并不同任务；用每行位置作为键则可能保留重复导出。稳定任务身份、调用身份及来源范围，比单纯选择一个哈希算法更重要。

## 旧入口的身份回退有什么代价

参考结构化入口使用 sessionId 或 Trace ID 回退，再结合调用 ID 或标准化错误签名去重。这个策略让缺少部分字段的数据仍能处理，但也意味着计数依赖输入形态。单个 Session 多任务时可能混在一起，跨 Trace 任务没有可靠映射时又可能被拆开。

因此，新的数据合同应区分“来源提供的真实字段”和“分析器生成的回退键”。报告要能说明当前 n_tasks 是什么定义。旧归档里的 n_sessions 有时只是兼容字段名，实际按 effective_trace_id / topic_id 表示任务，不能按字面解释。

## 恢复也需要身份和验收目标

订单查询失败后，天气工具成功，只能证明天气调用有成功迹象。订单调用改正日期并成功，也还要检查最终回答是否使用该结果，才能说业务目标达成。恢复分成调用恢复、步骤恢复和任务完成，会比一个 recovered 布尔值更清楚。

参考入口用后续任意未被判为失败的工具结果作为有限恢复代理。这一条件没有严格验证同工具、同目标或最终输出，容易产生误标；“没有识别成失败”本身也弱于明确成功。

新闭环可以先采用保守合同：只有原失败目标有明确纠正及成功证据才确认恢复，其余记录为恢复未知。这样可能增加复核量，但不会把无关成功当成已解决。以后若扩展自动判断，需要配对反例来验证收益。

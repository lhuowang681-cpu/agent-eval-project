# 轨迹太长时，怎样保留真正影响结论的内容

## 去噪解决的是上下文预算问题

一次 Agent 运行可能包含长工具清单、系统说明、重复消息、大段返回和图片编码。全部送进归因模型，会增加输入成本，也可能超出上下文限制。即使只做人审，几千条冗长记录也很难快速看清主线。

因此需要生成面向归因的精简视图。但精简不是简单取最后几行；目标是保留足以判断“输入从哪里来、在哪里变坏、怎样传播”的记录。

## 为什么父链和时间邻域都要考虑

父链告诉我们结构上的来源关系，例如工具返回属于哪个调用。时间邻域告诉我们错误前后实际发生了什么，例如后续是否原样重试。二者互补：相邻消息可能来自并发分支，父节点也可能不包含理解错误所需的全部背景。

参考去噪器先按 ID 去重，建立节点映射，找到错误节点，保留祖先，再补充前后时间窗口、部分后继和有意义角色。生成结果时会保留节点 ID、父 ID、保留原因和裁剪相关信息，便于把精简视图追溯到原数据。

## 一个压缩前后的例子

假设有八个节点：n1 用户指定查询日期；n2 正确工具格式；n3 无关长说明；n4 Agent 生成错误日期；n5 工具拒绝；n6 原样重试；n7 再次拒绝；n8 最终失败回答。

如果只保留 n5、n7，能看见两次错误，无法判断参数是谁生成。如果再保留 n4，知道出现了错误调用，但还不确定目标和要求是否曾可见。补上 n1、n2 后，才具备比较预期与实际的基础。n6 则支持重试处理是否合理的判断。

所以预算不足时应声明“当前视图只支持工具拒绝事实，内部责任尚不能确认”，而不是用两条错误文本完成所有归因。压缩质量取决于想回答的问题，而非单纯删除比例。

## 当前实现为什么仍可能裁掉重要祖先

参考实现先收集祖先，并不意味着最终全保留。候选节点多于 max_nodes 时，还会按错误、祖先等优先级截断。即使祖先被赋予较高优先级，预算足够小，也会有祖先被移除。

此外，节点仍在，但其正文前半段被保留、后半段被截掉，也可能删掉真正重要的限制条件。clean_text 会标记文本截断，但模型和报告必须使用这些标记来降低结论范围，否则“有节点”仍可能造成完整性的错觉。

## 应怎样设计更可靠的合同

原始输入是不可变的审计来源；精简结果是派生视图，包含保留 ID、删除 / 裁剪事实和预算配置；归因结果注明自己基于哪个视图。发现关键内容缺失时，可以回查原节点或明确弃权。

后续改进可以优先保证每个候选结论所需的最小证据组，再填充其他上下文；预算连最小组都装不下时，输出证据不足。这是候选设计，并非当前已完成的算法。

## 怎样判断压缩有没有帮助

要同时看输入体积、关键节点保留、父链断裂和归因结果。只报告减少了多少字符，可能掩盖“把根因来源删掉”的代价。给同一条轨迹设置不同预算，比较哪些事实还能成立，比只追求最高压缩率更符合工程目标。

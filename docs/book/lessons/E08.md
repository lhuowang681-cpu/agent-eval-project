# 规则与大模型怎样形成判断，为什么还要审核

## 先把分类与证明分开

分类回答“这条问题应该放在哪个标签下”。证明回答“哪些事实支持这个判断”。一个结果可以标签合法，却没有事实依据；也可以证据存在，却不足以排除其他原因。归因系统需要同时处理这两层。

taxonomy 是固定分类树。参考材料用 8 层 56 个模块描述平台职责，例如状态、上下文、模型参数或工具执行。它的工程作用是统一口径，让报表能够分组和比较；它不会自动识别真正原因。

## 模型路径实际经过哪些步骤

先整理轨迹中可用的字段，形成 payload；再把分类树和规则交给模型，要求返回 JSON；随后解析 JSON，检查模块合法性、整理类别和置信值，形成统一结果。这个顺序把自然语言判断接到可处理的数据接口上。

模型较适合综合较复杂的上下文，但也可能误读参数来源、忽略早期节点或引用不存在的 ID。结构化输出帮助程序读懂格式，不能让内容自动变真。

## 五层校验，用同一个例子讲清楚

假设模型返回“模块 L2.2，证据 n99，置信度 0.95”。第一层检查它是不是能解析的 JSON；第二层检查 L2.2 是否在分类树中；第三层检查 n99 是否出现在这次输入里；第四层检查角色、字段与结论是否一致；第五层检查证据是否真的支持内部责任。

如果 n99 不存在，第三层就失败。如果改成真实存在的 n1，但 n1 只是用户请求，也不能据它证明工具执行器发生异常，仍会在后面的支持性检查遇到问题。把不存在 ID 自动替换成真实 ID，不是修复，是制造新证据。

程序容易机械校验前三类结构条件。语义支持和反事实通常还需要规则约束、人工核对或经评测的辅助判断。把所有检查都称为 Schema 校验，会隐藏这些能力差异。

## 参考实现的边界在哪里

normalize_result 会检查模块、规整部分字段和置信值，对低置信或特定类型设置复核，但没有严格核验全部证据 ID 是否属于输入集合。模型提示词要求“引用真实节点”，与程序实际执行硬校验，是两个不同事实。

模型调用还有失败路径。参考实现部分调用错误会重试并生成归因失败结果；客户端创建也有自身的异常位置，不能笼统说任何异常都会进入同一 fallback。更重要的是，分类器失败不是业务轨迹根因，不能把模型服务不可用记成被测业务的 Observability 故障。

## confidence 应怎样理解

0.95 在这里首先是模型输出的数值，不是系统已通过样本验证的 95% 准确率。要把它用于阈值决策，应在人工核对样例上比较不同分段的实际正确程度，同时看覆盖率。温度设为零也不能代替质量评测。

## 为什么首轮仍先做确定性规则

明确失败状态、ID 存在性和任务去重不需要大模型猜测。先把这些合同建立好，可以构造稳定反例，未来模型输出也经过相同审核。规则的短板是覆盖有限，模型的短板是成本与错误不确定；二者的价值应通过同一数据、同一输出合同的对照来判断。

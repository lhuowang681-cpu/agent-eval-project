# 外部服务失败，什么时候仍有内部问题

## 单标签为什么不够

设订单服务返回 500，Agent 随后反复调用直至超出预算。说“外部故障”描述了服务失败，却漏掉多余调用；说“内部源码故障”又可能让人误以为 Agent 导致服务宕机。

更清楚的方式是输出双结论：direct_failure_cause 描述直接失败机制，agent_source_issue 描述有证据支持的内部处理缺陷。两种结论可以同时存在，各自引用不同证据。

## 从事实逐步走到责任

第一步检查输入合法性。模型发出什么，工具实际收到什么，是否满足当时的工具合同？第二步检查输入来源。错误参数可能来自用户、模型、上下文、前序工具或运行时转换。第三步看后续处理：是否知道失败，是否遵守预算，是否错误结束或遗漏结果。

例如用户明确要求一个不存在的资源，Agent 忠实调用后收到 not found，这不足以证明内部生成错误。只有产品合同明确要求预检，并且证据显示本该预检却未做，才可能另立内部问题。责任判断依赖预期行为，不只是异常关键词。

## 三条轨迹形成三种结论

| 情况 | 直接原因 | 有证据支持的内部判断 |
|---|---|---|
| 合法调用遇 500，按合同结束并告知 | 外部服务异常 | 未发现内部问题 |
| 合法调用遇 500，超过已记录的三次预算仍发起调用 | 外部服务异常 | 预算 / 重试治理候选 |
| 工具拒绝参数，但参数来源和合同缺失 | 参数被拒绝 | 证据不足，不能指定生成模块 |

第二种情况下，最早内部异常通常要找违反明确预算的那次内部决定，而不是把第一次外部 500 当作内部错误节点。证据应包含预算来源、累计调用及违反条件后的动作。

## 反事实修复不是一句万能建议

“加重试”或“优化提示词”过于模糊。有效反事实应说明：外部条件保持什么不变，只修改哪个内部机制，预期避免哪种后果。

对持续 500 的案例，可以说“预算守卫阻止第 4 次及后续调用，减少额外成本和等待”；不能说“预算守卫让服务恢复正常”。对错误日期的案例，可以说“调用前按可见合同校验并纠正格式，避免本次格式拒绝”。两种修复作用于不同机制。

反事实是归因合理性的检验，不是无需实验的因果证明。真正修复后，还应运行相同故障输入，确认改动没有引入提前终止或漏执行等新问题。

## 规范与旧入口的范围差异

来源规范一方面强调拆分外部故障和内部处理缺陷，另一方面对 MCP / plugin / unknown 设有开发榜硬分流。结构化入口也执行特定来源规则。因此，不应声称旧脚本已经完整表达所有外部工具上的内部治理责任。

自己的新合同可以把“外部调用事件”和“内部治理事件”作为不同对象，分别审核与统计，但要先明确设计和验收。这能避免把一个来源字段当作责任终审，也避免同一问题在多条泳道中重复计算影响。

## 判断不足时应该怎样交付

一份诚实结果可以写：已确认工具返回 500；未见参数无效证据；缺少完整重试预算与状态链；内部责任待复核。它比笼统“未知错误”更有用，因为审核者知道还缺哪些材料，采集侧也知道下一步应补什么。

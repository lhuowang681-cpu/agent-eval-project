# 先判断能否进入开发榜，再决定先修什么

## 同一份错误清单，为什么需要两次决策

假设一天收集到 1000 次外部账号权限错误，以及 3 个证据充分的内部结果回填缺陷。仅按频次排序，权限错误会占据榜首，但负责 Agent 源码的开发人员可能根本无法通过改代码恢复账号权限；少量内部缺陷却有清楚的修复位置。

因此，门禁回答“是否符合内部开发榜的范围与证据要求”，排序回答“合格问题中先做哪个”。先后次序很重要：结论还没有成立时，不应该靠高频、高影响或高置信度加分把它补成正式内部责任。

## 一条严格的内部准入链

首先存在内部异常：有实际输入输出偏离合同的节点。其次能够解释异常来源，并引用可回查的证据。再次能映射到合法责任模块，写出保持外部条件不变时的修复作用。最后排除只由关键词、工具名或最终错误推导责任的情况。

例如日期案例只有工具的 invalid date 文本，没有用户输入和参数来源，可以形成候选问题，却不足以正式认定内部参数生成缺陷。即便报错出现很多次，也应补采证据或人工复核。

## 开发优先分衡量治理偏好

参考开发分采用四维加权：可解决性 45%、内部证据 30%、用户影响 15%、去重频率 10%。可解决性关心改内部代码能改善多少；证据关心判断依据；影响关心任务阻断或降级；频率关心不同任务被影响的范围。

教学例子中四项分值设为 80、90、60、20：加权贡献分别为 36、27、9、2，总分 74。这个数表达相对处理顺序，不是“根因有 74% 概率正确”。权重来自治理选择，也不是对所有业务天然最优。

频率只占较小权重，是为了避免大量不可行动问题淹没明确内部缺陷。相应代价是高频问题的影响可能被低估；应通过人工看榜、业务损失和实际修复效果校准，而不是把公式当终审。

## 旧实现为什么不能等同严格合同

参考 evidence_score 会根据内部节点字段、证据列表、反事实文字和一些类别线索加分，部分类型还有分数下限。calculate_priority 再结合排除项与阈值决定 eligible。这是一组启发式数值与范围规则，没有逐条核验所有证据 ID 的存在性和语义支持。

因此，一个结果可能分数达标却引用 n99。新的工程合同应先做独立的硬校验，输出具体失败原因，再对通过项计算分数；而不把“评分函数返回 eligible=true”翻译成“因果归因已经证明”。

## 榜单怎样兼顾模块与问题

同一个模块可能出现多个二级问题。规范要求先在模块内选代表，再跨模块排序，防止 Top 5 全被同一个模块的多个近似问题占据。但这不是强凑五个模块；若只有两个模块证据合格，正式榜可以只有两个。

报告还应保留被过滤项目及原因，解释某个高频问题为何没进入首页。这样开发人员能区分“没有问题”和“问题被分流或证据不足”，也能复核治理策略是否合适。

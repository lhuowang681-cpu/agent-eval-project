# 同类错误怎样分组，严重度与频率怎样一起看

## 一个类别并不等于一个根因

“工具调用失败”可能包含超时、参数类型错、工具不可用。把它们加在一起可以描述总体噪声，却不能形成一项明确修复。收敛步骤试图把表面记录整理成较少、可解释的模式。

参考离线路径使用标准化错误签名。把请求 ID、随机数字等变化项归一化，保留 timeout、invalid type 等机制线索，再将相近记录分组。这样，同一种拒绝不至于因为调用 ID 不同而被拆成很多类。

签名是文本与规则意义上的模式，不自动证明共同因果根源。相同 timeout 可能来自服务慢、网络问题或预算设置。报告应称候选簇或模式，并保留进一步证据分析。

## 为什么严重度要与频率分开判断

严重度描述一次发生对用户造成什么后果；频率描述多少个不同任务受到影响。一次不可恢复阻断可能比许多轻微自愈重试更值得注意，也可能因为范围很小而不排最前。把两者先分开记录，才能看清排序背后的取舍。

参考规则将硬失败锚定为 S4、权重 8；已恢复但有额外摩擦的情况锚定为 S2、权重 2。再用“严重度权重 × log2(1+去重任务数)”给类别内候选簇排序。

## 手工算一次

簇 A 是已恢复问题，影响 3 个任务，教学得分为 2×log2(4)=4。簇 B 是硬失败，影响 1 个任务，得分为 8×log2(2)=8。B 频率较低却排在前面，因为其单次影响更严重。

对数意味着频次增长的边际贡献逐渐减小。任务数由 1 到 3，log 项由 1 到 2；由 3 到 7，才再增加到 3。它减轻高频模式无限放大的效果，却仍然依赖准确任务身份。把重试事件当成任务，公式再合理也会失真。

这套类别内分数与上一节四维开发分用途不同：前者挑一个类别内部更值得关注的候选模式，后者服务跨问题的开发治理。不能把权重和分母混在一起。

## 严重度的证据也会出错

参考实现存在不可逆风险关键词判断。例如正文出现“数据丢失”，可能来自事故事实，也可能只是说明“为避免数据丢失，请备份”。单纯命中词语不足以确认真实后果。

因此，确认最高严重度应回到状态、实际副作用和损害证据，而不是把规则固定 confidence 当作已校准质量。当前候选均不合格、样本为空、前两名非常接近时，也需要明确行为；旧实现中存在无 eligible 仍选择首项以及空输入边界，后续应单独验证。

## 最终交付应保留哪些解释

至少展示签名如何归一化、每簇有哪些任务、严重度依据、分数配置和待复核项。审核者可以据此判断“这是合理的治理选择”还是“同一关键词把不同问题混在一起”，而不是只能接受一个黑箱冠军。

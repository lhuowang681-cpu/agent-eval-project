# 报告怎样从结论走回证据

## 报告的用户是需要做决定的人

开发人员打开日报，希望知道今天先排查什么、影响了多少任务、凭什么这样判断。只有饼图或一个模块标签，还不足以采取行动；但把所有原始日志放进表格，又会让人找不到重点。

因此可以分三层：总览说明范围与过滤；问题层说明归类、影响和治理顺序；Case 层展示具体链路和原始字段。每层负责减少读者的认知负担，并允许继续往下核查。

## 用日期案例设计审计链

总览写“内部候选问题影响 1 个任务，包含 2 次失败事件”。进入日期格式问题后，看到用户目标、实际参数、工具拒绝和原样重试。再点击证据，看到 n1 的日期、n2 的工具合同、n3 的调用参数与 n4 的返回。

这样审核者可以质疑“要求是否真的可见”“是模型生成还是转换造成”“两次调用是否属于同任务”。能够被质疑并回查，正是审计报告的价值，而不是报告不够确定的缺点。

## 报告至少要保留哪些字段

任务和 Trace 身份说明分析对象；直接原因与内部候选说明两层责任；异常与暴露节点说明发生顺序；证据 ID 与关键原值支持结论；反事实说明修复作用；复核状态与缺失信息限制结论范围。原始文件、记录位置和分析配置用于复现。

只写“参数错了，建议优化”几乎不能核查。写“n3 发出的 date 为今天，n2 要求 YYYY-MM-DD，n4 拒绝该输入；责任模块待核对”则已经是一条可讨论的工程判断。

## 聚合为什么也要查实际逻辑

参考 aggregator 对分类结果按类别和模块分组，并统计行数。如果输入一行是事件，结果就是事件行数；若输入一行是 Trace 级分类，结果含义又不同。groupby 不会自动理解业务任务，也不会自动去重。

新的报告应分别给出输入行、有效 Trace、失败事件、受影响任务与复核数量。每个数量的分母、回退身份和排除范围要一致。不同图表用不同单位也可以，但标题必须明确。

## 不确定性不能在展示时消失

底层是候选归因，表格标题就不应变成“已确认根因”；底层节点经过裁剪，报告不能把它呈现为完整轨迹；被排除的外部问题应有去向，而不是从总数里无声消失。

可以同时提供正式内部榜、外部依赖、证据不足和潜在改进等泳道。它们服务不同处理者。报告不是把所有问题都变成开发任务，而是把正确问题送给正确的处理环节。

## 首轮为什么选 JSON 与 Markdown

JSON 便于机器读取和自动检查，Markdown 便于人工复核和版本比较。同一份已校验结果生成两种视图，能减少口径分叉。先验证它们的身份、数量和证据一致，再考虑 Excel 模板、图片和交互页面，会让工作重点落在可信内容上。

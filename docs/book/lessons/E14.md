# 时延、首 Token 和成本应该怎样计算

## 指标先定义对象，才有数字

一个任务可能经过三次模型请求和两次工具调用。用户等待多久、某次模型多久吐出第一个 Token、总共花费多少，是三个不同问题。它们可以帮助定位慢在哪里，却不能共享一个模糊的“响应时间”。

端到端延迟关注一条 Trace 约定的开始和结束。TTFT 关注一次 Generation 从其约定请求起点到首 Token 的等待。Generation 是一次模型生成观测；一个 Trace 可以包含多个。工具耗时和排队也会影响用户等待，但不应自动计入每次模型自身 TTFT。

## 用时间线区分

教学例子中 Trace 从 0 秒开始，模型 1 在 0.2 秒发出请求，0.8 秒收到首 Token，1.5 秒结束；工具在 1.6 到 3.6 秒执行；模型 2 在 3.7 秒请求，4.0 秒首 Token，4.5 秒结束，Trace 在 4.6 秒结束。

按这份观测定义，端到端是 4.6 秒，两个 TTFT 分别为 0.6 秒与 0.3 秒。不能把 4.6 秒作为两次模型的 TTFT，也不能仅相加 TTFT 就认为是总等待。真实数据若定义了不同起点，应按数据合同解释。

## 缺失费用为什么不能填零

设一个 Trace 的三次 Generation，费用分别为 0.01、0.02、未知。当前已知费用合计 0.03，但完整 Trace 总成本未知。可报告金额已知部分与 2/3 的调用记录覆盖率；这不是“已覆盖三分之二的真实费用”，因为缺失的那次可能特别贵。

费用还需要币种、计价版本、Token 来源以及缓存等规则。没有数据就保留未知；零只用于已确定确实没有费用的情形。否则某个版本缺日志更多，反而会在报表中显得更省。

## 最差样本和分位数需要固定算法

最终三指标归档的 Top 最差 10% 使用 K=max(1,ceil(N×10%))，以第 K 条真实样本作为边界。这里的排序方向、有效样本过滤和 N 必须先确定。例如 11 个有效延迟样本，K=2，取最慢的两条；若 N=0，则应报告无数据，而不是硬造一条。

P95 也需要说明计算约定。不同软件可能使用插值或不同经验分位数方法，小样本时差异尤其明显。做版本对比时应固定算法，并比较相同任务分布、模型和并发条件。

## 时间窗与采样偏差

来源最终归档说明日报为 24 小时、三指标为 30 天，早期材料出现过其他窗口。窗口变化会改变样本，不能把不同口径数字直接当优化前后。

如果只分析 badcase，得到的是失败候选样本的成本和时延，不是全体请求的整体表现。TTFT 只对有首 Token 记录的调用计算时，还需报告缺失情况，否则结果可能只代表更容易被观测的那部分任务。

学会指标，首先是能解释每个数字对应什么对象、分母、时间窗和未知部分。精确的小数位不会让错误口径更可信。

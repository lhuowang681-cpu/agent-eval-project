# 怎样阅读历史实验，并设计自己的复现

## 报告首先是一份带条件的证据

历史实验能告诉我们作者当时研究了哪些机制、采用什么输入、观察到什么现象。它不自动等于当前版本仍然有相同问题，也不等于现在的机器能按原步骤复现。

参考包里有平台原版、修订版和历史审查材料。阅读时应先确定报告针对哪个版本，再看该机制在当前文件中是否变化。如果版本错位，就可能用旧缺陷解释新代码，或把后来的修订错误地当作旧实验已经验证。

## Mock、存根和真实服务各证明什么

Mock LLM 可以固定返回纯文本、持续工具调用或特定错误，便于控制变量，测试调度、回填和终止。它不能测真实模型是否理解业务问题。私包存根能让部分工程路径启动，也可能缺少真实依赖的副作用和性能。

PGlite 等替代环境可以支撑某些数据库操作验证，但实际部署的连接、并发和基础设施条件不同。若某项实验没有 Redis，就不能由该结果推出真实 Redis 步锁和分布式恢复已通过。

这不是说替身实验没有价值，而是每种证据只回答它真正覆盖的问题。

## 建立四栏证据账本

| 类别 | 例子 | 合理表述 |
|---|---|---|
| 来源报告 | 旧文档记载循环失控 | 某报告在特定条件下观察到现象 |
| 源码可见 | 修订服务加入步数 / 中断逻辑 | 机制存在，可以解释设计意图 |
| 本轮实测 | 固定输入在当前版本运行得到记录 | 当前条件下验证了对应行为 |
| 线上观测 | 真实部署、真实负载、持续采样 | 只在观测覆盖范围内说明表现 |

向下一栏升级需要新证据，不能靠更强语气。尤其不要把来源报告中的数字直接写进个人成果。

## 怎样做一个最小前后对比

先选单一机制，例如“超预算后是否停止安排新调用”。固定输入与模型替身、步数预算、工具返回和观测字段，分别运行基线与修订。记录调用数量、终止原因、最终状态和异常日志，而不只看命令退出成功。

然后检查代价：限制是否让正常长任务提前结束？取消是否丢掉最终消息？异常分支是否多一次模型调用？一个修复实验既要验证目标故障消失，也要检查最相关的正常路径。

结果文件应保留版本、配置、输入、原始输出和限制。没有真实模型时明确只完成工程控制验证；没有性能提升时如实记录持平或回退，仍然可以形成有价值的取舍。

这类经历在面试中的说服力来自具体因果链：为什么构造这个输入，它暴露哪个机制，改了什么，哪些结果支持结论。它比借用别人一组大幅提升数字更能经受追问。

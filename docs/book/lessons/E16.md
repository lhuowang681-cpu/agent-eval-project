# 评测集怎样暴露归因错误

## 先写应有行为，再看程序输出

如果把当前程序的结果抄成标签，再运行同一个程序，评测只能证明它与自己一致。有效样例应根据业务合同和人工可见证据定义期望，尤其要包含会让粗糙规则犯错的反例。

首轮可以从五类开始：纯外部失败、内部输入错误、原任务恢复、同任务重复报错、证据不足。每类至少做一对只改变关键因素的案例，让结论变化有明确理由。

## 一对样例比十个近似成功例更有用

在 A 中，合法参数遇 500，Agent 按合同停止；在 B 中，外部 500 完全相同，但 Agent 超过明确预算仍发起调用。两者直接原因相同，内部治理判断应不同。

在 C 中，错误日期由 Agent 生成；在 D 中，用户明确指定错误参数，产品又没有预检义务。最终工具错误相同，责任结论不应只靠 invalid date 关键词固定不变。

另外加入引用 n99、关键父链被裁剪、后续无关工具成功等反例，分别检验证据存在性、完整性与恢复合同。每条样例标出应引用节点、可确认事实、可接受的弃权原因和不应出现的结论。

## 指标要分别衡量哪一种能力

内部责任精确率关注系统报出的内部问题中有多少真的成立；召回关注真实内部问题中识别出多少。非内部样例上的误报率关注外部或证据不足被错误升级的比例。证据有效性关注所引用 ID 与原数据的关系，语义支持要另查。

覆盖率描述有多少样例得到系统允许作出的明确判断，弃权率描述保留复核的部分。它们的定义必须与准入规则一致，不能把任意输出字符串都算有效覆盖。

教学数字例子：12 条样例中 5 条有明确内部问题，系统报出 4 条内部问题，其中 3 条正确，则内部精确率是 3/4，召回是 3/5；其余 7 条非内部样例中有 1 条误报，则该组误报率是 1/7。若共有 6 条形成有效明确结论，覆盖率为 6/12。数字只是说明分母，不是当前成绩。

## 怎样避免用评测集调出假进步

如果每次看到错误就把特定文本写进规则，再用完全相同的样例报告提升，很难说明泛化。样例数量允许时，应保留未参与改规则的部分；小数据集也可以至少区分开发反例和独立检查样例，并说明规模限制。

未来比较规则与规则加模型时，输入、合同、标签和证据门禁应相同；同时记录接口失败、调用数、成本和弃权。模型判断更丰富但误报增加，或规则更保守但覆盖下降，都是需要解释的实际取舍。

## 人工核对的工作是什么

人工不是把模型 confidence 当分数抄进去，而是逐条核对输入来源、异常节点、反事实和结论边界。有分歧时保留理由和标签版本。先得到少量可信样例，再扩展到 30～50 条，会比大量未经核对的标签更适合首轮个人项目。

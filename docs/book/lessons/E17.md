# 怎样把参考材料变成自己的离线小闭环

## 第一版的目标是什么

输入一份合成 JSONL，得到一份能回到具体证据的 JSON / Markdown 报告。它应区分直接故障和内部候选，拒绝不存在的证据 ID，按清楚的任务合同计数，保留证据不足。这个范围足够形成完整演示，也能对应参考实现中的明确缺口。

本节是待开发设计，不表示归因器已经运行。前面的教材与阅读器是学习产物，业务应用的代码和验证需要另行交付。

## 模块边界围绕数据流划分

适配器把原始行转成规范 Trace，保留行号和来源。失败检测器生成有调用身份与失败信号的事件。规则分析器生成候选判断，不直接决定正式准入。验证器检查证据、模块和责任合同，并给出拒绝或复核原因。聚合器按规范身份计算不同层次的数量。报告器从同一份已校验结果生成机器版与人读版。

这样拆分的目的不是凑模块，而是让每一步有可检查输入输出。模型以后接入时，只替换或补充候选判断环节，不能绕过证据验证与代码计数。

## 数据合同先作决定

先定义 task_id、trace_id、node_id、tool_call_id 的作用和缺失处理，再定义结果中的直接原因、内部候选、最早异常、证据列表、反事实、准入状态和复核原因。原始字段、规范字段和派生判断应能区分。

未知来源不应自动伪装成已确认外部；没有匹配失败不应自动表示成功；有真实证据 ID 不等于语义已经成立。这些合同会直接进入样例与验收，而不只是写在说明文档里。

## 一个增量应该怎样交付

以证据 ID 校验为例：先准备结论引用 n99 的合成输入；说明期望是阻止正式准入并输出原因；再实现校验；记录真实运行结果，并加入引用存在但不支持结论的下一层反例。这样可以明确说“新增了什么、解决什么、仍没解决什么”。

每个增量保留 Spec、输入、预期、代码版本、原始输出和失败记录。Codex 负责主要编码，你重点核对合同、理解设计与判断结果；理解不等于背函数名，也不要求手写全部模块。

## 首轮为什么暂不接数据库和真实模型

小批量离线文件已经能支持保存、比较和复现。引入数据库会增加迁移和部署问题，引入真实模型会增加接口、成本与输出不确定性。当前最先要验证的是证据与计数合同，外部依赖不应成为它们的前置条件。

等需要重复分析较多批次、多用户共享或真实语义对照时，再按需求增加存储与模型适配。选择简化方案的理由必须具体：减少什么依赖，暂时放弃什么能力，以后怎样扩展。

## 首个验收点

五类合成场景可以完成本地处理；无效引用被拦截；同任务多个失败不重复增加影响任务数；证据不足明确复核；同输入和固定配置得到可比较输出。验收结果证明工程闭环，不能单独宣称真实模型准确率或生产性能。

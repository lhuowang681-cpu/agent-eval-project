# 服务端执行与可靠性：一次较完整的工程讲解

2026-10-23。关联B1—B4、C1—C4及E02/E03。本文为教练讲授材料，不表示用户已独立验收，也不表示本轮部署或运行了参考平台。参考源码、风险推演和新增设计建议分别说明。

## 从执行循环到服务端

一个订单任务可能经历模型规划、工具查询、再次模型处理以及人工等待。服务端若让整个任务依附一个HTTP请求，长耗时会碰到连接、网关、进程生命周期等限制。分步调度让每次处理有限工作，保存当前结果，再安排下一步；前端可通过另一个事件通道观察进展。

参考服务端包含本地调度和QStash调度：本地使用进程内回调，远端队列安排后续HTTP请求。二者可以共享调度接口，但进程退出后的恢复保障不同。队列也不是Runtime本身：前者安排何时在哪里执行，后者推进当前状态和指令。一个Runtime step可能包含多个指令，不把它机械等同于一次模型请求。

教学路径：operation创建→调度本步→领取步锁→加载状态→Runtime推进→保存结果与事件→检查终止/等待/预算→调度下一步或结束。

## 数据责任与边界

- 业务数据库：用户消息、操作业务记录等需要长期保存的数据；参考服务也同步部分operation跟踪记录。
- Redis运行态：当前快照、运行事件及协调信息等，具体过期策略属于恢复合同。
- 队列：待执行工作和投递身份，不是完整业务历史。
- 观测与分析记录：供排查的参数、返回、关系和时间等，不自动拥有完整可恢复业务状态。

Redis并非只能作缓存，此处按参考系统的职责划分说明。使用多个存储也不自动得到原子一致性；运行态过期后，能否恢复应取决于真实的持久数据和重建流程。

## 并发锁与重复副作用

队列重投或并发请求可让两个执行方进入同一operation/step。参考实现以operationId和stepIndex领取带35秒租约的步锁，并在finally释放。锁可以减少同时进入，但不能凭此宣称工具仅执行一次。

教学窗口：A调用外部工具成功→保存结果前进程退出→锁到期→B重试并读取旧状态→再次调用工具。对查询主要是重复消耗，对发送、创建或扣款则可能重复产生业务动作。

需要区分调度身份、真实调用身份和业务幂等身份。外部接口若支持稳定幂等键，重复同一业务动作可返回已有结果；若不支持，系统应保留结果未知并查询确认或人工核对。仅在本地写一行日志不能对外部动作实现原子一次执行。

租约过期时还可能出现A未结束而B已获新锁。旧持有者的迟到状态需要版本约束；释放锁也应核对持有者身份，避免误删新锁。参考AgentStateManager.ts的releaseStepLock直接删除键，未见持有者比对，因此该窗口适合定向并发验收。这里是静态风险分析，没有本轮并发复现结果。状态版本约束与业务幂等解决不同边界，不能相互替代。

## 保存成功与调度成功是两个事实

参考服务先saveStepResult，后根据继续条件scheduleMessage。需要验证两个窗口：保存后、调度前退出，任务可能停住；调度后、确认前退出并重试，则可能重复投递。

通用改进方案可将权威状态变更与待发送工作写入同一数据库事务，再由投递器重发未确认工作，即事务发件箱。该方案要求设计明确的事务存储边界；不能把Redis写入与数据库插入随意称为同一个事务。投递端仍可能重复，消费端仍需去重和副作用幂等。这里是设计建议，不声称参考工程已实现。

## 取消、预算与审批

取消的典型丢失更新：Worker读到running→用户写interrupted→Worker把旧快照整体写回running。参考修订版用独立持久中断标记避免普通快照覆盖，并记录活动Runtime以尽力中止同进程执行；跨进程依赖持久标记及检查点。取消受理、停止调度、当前调用中止和撤销已完成动作是不同事实，不能用取消接口成功代替全部验证。

预算控制分别考虑总步数、累计成本和单次超时。软收敛要求模型整理已有结果，硬闸在其不配合时停止继续调度；成本估算及在途调用可能带来超出预算的窗口，需要定义度量和检查时机。参考修订版有默认预算、forceFinish与额外硬闸，机制可静态核对；生产效果仍需实验。

审批必须绑定原调用及参数，等待→批准/拒绝→恢复应有可回查关系。批准后改变危险参数不能沿用旧授权；重复批准需要避免重复动作。参考修订服务补齐内置工具manifest，其他工具来源仍有各自配置边界，不能据此声称全部工具的策略均已完整。缺少策略信息和已知无需审批不是同一事实；保守处理方式应由产品合同规定。

## 需要采集什么，怎样验证

建议的分析字段包括：operation/step及投递身份、Trace/节点/调用关联、工具输入和实际返回、状态版本、调度时间、步骤起止、工具起止、预算、取消和审批事件及结束原因。它们是分析所需字段建议，不代表现有包已全部集成到Langfuse。界面流式事件、业务持久记录和分析Trace不是自动完整同步的同一份数据。

队列等待、模型耗时、工具耗时和端到端耗时分开计算；有并行时不能简单相加各调用时间得到端到端耗时。

| 固定条件场景 | 应检查的约束 | 关键证据 |
| --- | --- | --- |
| 同一步重复投递 | 不重复提交同一业务动作 | operation/step、锁持有者、调用及幂等记录 |
| 外部动作后、保存前退出 | 识别已执行或结果未知，避免盲重试 | 外部结果凭据、业务幂等身份、保存边界 |
| 状态保存后、调度前退出 | 能发现停滞并恢复下一步 | 状态版本、调度记录和恢复事件 |
| 执行中取消 | 后续调度停止，晚到结果不恢复运行 | 取消标记、Worker读写时间和后续动作 |
| 模型持续提出工具调用 | 软收尾后硬闸确实阻止继续 | 步数、成本、终止原因和最后调用 |
| 重复批准或批准后修改参数 | 不重复执行，不扩张授权范围 | 原调用/参数、批准事件和实际动作 |

这些是应执行的验证设计，本轮没有运行。后续归因从最早可见偏离预期的边界提候选：重复动作可能涉及重投/幂等；查询有结果但最终回答缺失可能涉及回填或上下文；取消后继续可能涉及控制信号或迟到写回。最终报错位置本身不足以指定内部责任模块。

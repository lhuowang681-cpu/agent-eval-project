# 01 先理解被测Agent，再理解归因对象

状态：现有代码的教学拆解；不是原作者历史开发记录。每个任务建议45～90分钟，第一次以走通场景为主，之后按复述暴露的缺口补课。

## 本章前置知识

消息角色、工具调用、状态机、数据库/缓存/队列各是什么；不必通读整个上游平台。

## 本章业务链路

请求→Service→状态→Brain决策→指令→Executor→事件与持久化→下一步调度。

## 数据和责任合同

source-reference包含原版和审查修订版；归因流水线与被测平台是两个工程层次。参考来源不等于用户本人开发。

## E01 划定自己的项目范围

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据

**为何需要这一步**

原包同时有平台、审查和归因报表；不先划界就会把别人完整平台当成自己的项目。

**代码入口**

`README.md`。路径相对于agent-eval-project；这是参考源文件。先读合同与分支，再看实现细节。

**按顺序完成**

2. 写1页关系图：平台产出轨迹，采集器取得轨迹，归因分析得出结论，报表展示结论。
3. 标注哪些是当前可读参考、哪些环境未恢复、哪些是准备自己新增的实现。

**失败场景与边界**

看过架构报告不等于实现或复现报告中全部功能。

**本任务验收产物**

产出范围声明：主线、支撑模块、非目标、来源和本人未来贡献位置。

**回答必须包含的要点**

## E02 拆开Brain、Runtime和Executor

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

把决策和有副作用的执行混在一起，会难以测试、重放和定位失败。

**代码入口**

`source-reference/runtime-reviewed/packages/agent-runtime/src/core/runtime.ts`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 对照GeneralChatAgent.ts和core/runtime.ts找state/phase、instruction和执行返回。
2. 选一次工具调用，追踪指令如何到RuntimeExecutors，再回写状态/事件。
3. 区分服务端队列一步重入和客户端循环；找PG、Redis状态及事件分别在哪一层使用。

**失败场景与边界**

执行器调用失败与Brain选择错误是不同问题，最终错误在Executor暴露不代表根因必在该模块。

**本任务验收产物**

产出一次工具调用的时序，逐步标注可观察节点和副作用。

**面试追问**

为什么不把所有逻辑写在while True里？

**回答必须包含的要点**

职责拆开有助于隔离副作用、测试状态转换和适配不同运行环境，但仍需要预算和终止治理。

## E03 原版与修订版怎样比较

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

旧故障报告可能对应已修订代码；不能把历史缺陷直接说成当前复现结果。

**代码入口**

`source-reference/runtime-reviewed/src/server/services/agentRuntime/AgentRuntimeService.ts`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 与runtime-original对应文件比较max steps、成本、中断标记、active runtime和工具manifest相关段落。
2. 对每个差异写触发场景、旧代码行为、修订意图、待验证结果，不猜作者亲历。
3. 读历史PLAN-REVISION和性能报告，登记Mock/PGlite/私包存根等实验条件。

**失败场景与边界**

默认步数上限存在仍不证明每个外部执行都能及时取消；配置和持久化路径还要独立验证。

**本任务验收产物**

交付至少3条差异卡，分别标“源码可见”“历史报告”“尚需复现实验”。

**面试追问**

你怎么证明修复有效？

**回答必须包含的要点**

需要同输入同条件的前后复现；仅凭代码diff只能解释修复意图和机制。

## 本章结束检查

合上代码，用一个例子讲述本章链路。遇到无法解释的节点再回到对应文件；不需要抄写全部实现。把仍未验证的结论写进学习记录，不靠猜测补齐。

验证练习先用合成材料和离线依赖。本章列出的是学习操作和预期产物，并未声称这些实验已经执行。

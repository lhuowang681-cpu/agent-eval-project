文字中提到失败、模型复述错误与实际工具失败需要区分。

**代码入口**

`source-reference/attribution/structured_jsonl_attribution.py::failure_envelope`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 读extract_messages/scan，追踪assistant的tool_calls与role=tool如何按ID配对。
2. 构造成功结果含error一词、明确status失败、非零exit code、无可解析body四种内容，按代码预测检测结果。
3. 读tool_source的名称启发式，说明builtin/mcp/plugin/unknown如何进入不同报表。

**失败场景与边界**

工具名称规则可能误判来源；未知来源不是已证明外部没有内部责任。

**本任务验收产物**

## E06 任务去重与恢复标记

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

一次任务可有多个失败节点；后面出现成功工具不一定表示原任务成功。

**代码入口**

`source-reference/attribution/structured_jsonl_attribution.py::scan`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 找sid、eventid和去重key，分别说明有/无sessionId与tool_call_id时的回退。
2. 用两个Trace属于同任务、一个Trace多个错误的例子算事件数、Trace数、任务数。
3. 查看recovered赋值条件，构造“失败后另一个无关工具成功”，说明该信号为何只是有限代理。

**失败场景与边界**

字段叫n_sessions不能证明源数据有真实Session。恢复标记不能直接当任务完成率。

**本任务验收产物**

产出去重口径说明及一张3种计数表，明确哪些ID缺失会改变结果。

**面试追问**

任务成功率的分母应该是什么？

**回答必须包含的要点**

预先定义可独立验收的用户任务，不能用工具调用次数或原始报错行数替代。

# 03 保留因果信息，再做规则或模型判断

状态：现有代码的教学拆解；不是原作者历史开发记录。每个任务建议45～90分钟，第一次以走通场景为主，之后按复述暴露的缺口补课。

## 本章前置知识

树/父子节点、结构化输出与Schema校验、分类树和人工标注。

## 本章业务链路

原始节点→去重/去噪/裁剪→taxonomy约束→模型归因→归一化→复核/弃权。

## 数据和责任合同

压缩输入不能悄悄丢关键因果证据；模型输出能解析不代表其证据引用和根因成立。

## E07 去噪保留了什么，牺牲了什么

- [ ] 能解释业务问题

**为何需要这一步**

节点过长会浪费上下文；裁剪过度会只剩最后错误而丢失错误来源。

**代码入口**

`source-reference/attribution/trace_denoiser.py::denoise_trace_nodes`。路径相对于agent-eval-project；这是参考源文件。先读合同与分支，再看实现细节。

**按顺序完成**

1. 手画10节点轨迹：用户输入→错误参数→工具失败→重试→失败，补上无关长system节点。
2. 按代码走去重、错误标记、祖先链、时间邻域、后继和角色选择；再将max_nodes设得很小做纸面推演。
3. 查看clean_text和裁剪标记，说明原始证据如何保留、模型应如何知道上下文不完整。

**失败场景与边界**

先全收祖先再按max_nodes截取仍可能失去祖先，不能宣称父链完整性无条件成立。

**本任务验收产物**

交付保留/删除节点清单及一个会影响归因的裁剪反例。

**面试追问**

压缩率高是不是越好？

**回答必须包含的要点**

需同时测证据保留和归因质量，省Token不能以切掉关键因果节点为代价。

**为何需要这一步**

taxonomy约束词表，normalize规整输出；两者都不能单独验证事实。

**代码入口**

`source-reference/attribution/llm_classifier.py::normalize_result`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 读taxonomy的8层56模块，选择参数生成、上下文、工具执行、Observability说明职责差别。
2. 从build_payload→_extract_json→normalize_result跟踪输入和输出，标出错误模块、低置信与fallback。
3. 构造合法模块但证据node ID不存在的结果，查当前是否严格拒绝；将缺口记录为未来测试，不能说已修复。

**失败场景与边界**

模型自己给0.9不是90%准确率；重试和response_format回退也可能增加调用成本。

**本任务验收产物**

产出分类JSON教学样例、两个无效样例和一份当前校验/待补校验表。

**面试追问**

用了JSON格式为什么还需要验证？

**回答必须包含的要点**

JSON只提供语法结构，还需校验枚举、引用ID、字段一致性、证据支持和不确定状态。

## E09 外部直接原因与内部可修复缺陷

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

外部500和内部无限重试可同时成立，单标签会掩盖治理空间。

**代码入口**

`source-reference/attribution/developer_source_attribution_spec.md`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 阅读first_internal_abnormal_node_id、internal_evidence_node_ids和counterfactual_fix等合同。
2. 对比“服务不可用后正确结束”和“服务不可用后无上限重试”，写不同的直接原因与内部责任结论。
3. 写反事实：保持外部条件不变，仅修改哪个内部模块，会避免什么后果；证据不足时保留待复核。

**失败场景与边界**

不能仅由最后的工具参数拒绝，倒推出一定是Agent自己生成的错误参数，用户指定等来源需检查。

**本任务验收产物**

完成2条对照Case卡：触发、最早异常、传播链、证据节点、修复点和不确定性。

**面试追问**

如何避免把所有外部失败归给Agent？

**回答必须包含的要点**

明确直接故障和内部机制两层，并以内部异常、节点证据及反事实改善作为内部责任依据。

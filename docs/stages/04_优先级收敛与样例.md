# 04 从归因结论走到治理顺序

状态：现有代码的教学拆解；不是原作者历史开发记录。每个任务建议45～90分钟，第一次以走通场景为主，之后按复述暴露的缺口补课。

## 本章前置知识

加权分数、对数、分组去重、向量相似度的含义。

## 本章业务链路

分类结果→内部可行动门禁→多维开发优先级；另一路：类别→根因簇→严重度/任务影响排序→代表Case。

## 数据和责任合同

开发优先分、类别内根因排序、代表样例选择是三个算法，分数不是因果概率。

## E10 开发优先分与门禁分开看

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

频繁但不可修或证据不足的问题，不应仅因数量大排到开发队列前列。

**代码入口**

`source-reference/attribution/development_priority.py::calculate_priority`。路径相对于agent-eval-project；这是参考源文件。先读合同与分支，再看实现细节。

**按顺序完成**

1. 找四个分项及45/30/15/10权重，记录模块先验、排除actionability和不同类别门槛。
2. 对一个高频外部故障和一个低频明确内部错误做纸面比较，说明eligible门禁与分数排序的区别。
3. 对照E09严格合同，指出当前evidence_score的启发式补分，不等于逐字段强制因果审核。

**失败场景与边界**

score达到阈值可能仍缺真实node证据；规范比实现更严格的位置应列为缺口。

**本任务验收产物**

产出分数分解表和一条“分高但不应准入”的教学反例。

**面试追问**

为什么频率只占10%？

**回答必须包含的要点**

这是治理偏好，优先考虑可修复性和证据；需结合业务目标校准，不能说该比例天然最优。

## E11 类别内怎样收敛和排序

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

一个报错类别可能有多种根因；最高频不一定最严重。

**代码入口**

`source-reference/attribution/cause_convergence.py::converge`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 阅读normalize_text/signature/severity_for/score，区分签名分组、严重度和去重任务计数。
2. 以3次低风险与1次高风险为例，按severity_weight×log2(1+n_tasks)解释排序。
3. 检查eligible为空、置信度阈值和前两名接近的处理，解释为何还有复核需求。

**失败场景与边界**

规则关键词和固定置信值不能证明真实不可逆损害，S5需实际后果证据。

**本任务验收产物**

写出2个根因簇的计数、严重度、排序及未解决的证据问题。

**面试追问**

对数频率为什么有用？

**回答必须包含的要点**

降低重复高频的无限放大，让严重度仍能影响排序；其业务效果需验证。

## E12 代表Trace为什么有两套算法

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

代表Case用于让人看懂簇，不能把“最像其他文本”与“根因最准确”混为一谈。

**代码入口**

`source-reference/attribution/cause_convergence.py::medoid`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 用3段简短错误描述推演TF-IDF、余弦距离和平均距离最小的真实样例。
2. 对照representative_case_selector.select_representative_trace的频率/签名/完整度选择，不把两者说成同一实现。
3. 分析medoid成对相似度的O(N²)代价；为大簇设计采样/候选预选方案，但标为尚未实施。

**失败场景与边界**

文本最常见的样例可能证据很差；代表性、证据完整度和可解释性要分别检查。

**本任务验收产物**

交付两种算法适用范围表，以及一个文本代表性与证据强度冲突的样例。

**面试追问**

为什么不直接取最长Trace？

**回答必须包含的要点**

长度可能只是噪声或重复；应依据代表性与证据需求，并保留选择依据。

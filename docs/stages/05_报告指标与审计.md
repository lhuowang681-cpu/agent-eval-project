# 05 报表要让人回到证据，指标要说清口径

状态：现有代码的教学拆解；不是原作者历史开发记录。每个任务建议45～90分钟，第一次以走通场景为主，之后按复述暴露的缺口补课。

## 本章前置知识

分位数、平均值、时间窗、缺失值、聚合粒度。

## 本章业务链路

结果表→分类聚合→代表Case→可审计报告；另有平台Latency/TTFT/Cost三指标材料。

## 数据和责任合同

报表呈现不应增强底层结论的确定性；费用和性能必须绑定数据时间窗、运行环境与覆盖率。

## E13 结果怎样回到原始轨迹

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

只展示根因名称和柱状图，审核者无法验证为什么这样判断。

**代码入口**

`source-reference/attribution/aggregator.py::aggregate`。路径相对于agent-eval-project；这是参考源文件。先读合同与分支，再看实现细节。

**按顺序完成**

1. 从classified输入到分模块/类别聚合，检查缺失列、unknown和复核结果怎样处理。
2. 找高频Case报表及代表选择入口，画出分类→聚合→Case→原Trace/node的审计链。
3. 给一条假设结论补任务ID、节点、原始字段和裁剪说明；没有证据时明确空缺。

**失败场景与边界**

报表中的排序、颜色和标题不能把candidate root cause升级成confirmed root cause。

**本任务验收产物**

产出一条可回溯审计卡和一条证据缺失时的展示草案。

**面试追问**

你的报告和普通日志统计有什么区别？

**回答必须包含的要点**

应提供任务去重、内部责任分层、证据回链和可复核的治理建议，并诚实保留不确定性。

## E14 三指标先学口径

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

TTFT、端到端延迟和费用的来源粒度不同；缺失generation会低估或偏置结果。

**代码入口**

`docs/EXISTING_CODE_SPEC.md`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 定义Trace端到端时延与Generation首Token时延，说明开始/结束点及流式/非流式差别。
2. 将Generation费用按Trace汇总，标注缺失值与覆盖率；禁止默默把未知填0。
3. 区分原包最终三指标归档的30天/24小时与早期7天说明，本目录没有复现该看台服务。

**失败场景与边界**

Mock LLM历史吞吐和模型自报Token不是当前真实部署成本/性能。

**本任务验收产物**

完成指标字典：公式、粒度、时间窗、数据源、缺失处理与限制。

**面试追问**

P95为什么会变化？

**回答必须包含的要点**

可能由任务分布、模型、并发、外部工具和缺失采样共同影响，需要保持条件并拆分阶段时延。

## E15 怎样阅读历史实验而不夸大

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

旧报告有真实来源价值，但条件不同，结论适用范围也不同。

**代码入口**

`source-reference/historical-analysis/`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 给架构/功能/性能报告逐项登记版本、配置、数据、mock依赖和报告日期。
2. 把“报告声称”“源码可见”“本地复现”“当前线上”分成四栏，移入对应证据。
3. 对高Token或调用次数案例解释可能机制，列出新实验要控制的变量，而不填虚构当前分数。

**失败场景与边界**

历史报告存在不代表当前机器可按同命令运行，更不代表用户本人当时参与。

**本任务验收产物**

交付一页证据等级表和一项可复现计划。

**面试追问**

你项目优化了多少？

**回答必须包含的要点**

只引用自己同口径验证过的前后结果；历史他人数据用于说明来源和复现目标。

## 本章结束检查

合上代码，用一个例子讲述本章链路。遇到无法解释的节点再回到对应文件；不需要抄写全部实现。把仍未验证的结论写进学习记录，不靠猜测补齐。

验证练习先用合成材料和离线依赖。本章列出的是学习操作和预期产物，并未声称这些实验已经执行。

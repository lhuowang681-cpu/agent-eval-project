# 06 把参考材料变成自己的可验证能力

状态：现有代码的教学拆解；不是原作者历史开发记录。每个任务建议45～90分钟，第一次以走通场景为主，之后按复述暴露的缺口补课。

## 本章前置知识

前5章；测试样例、人工标注、精确率/召回率和覆盖率。

## 本章业务链路

明确合同→合成样例→离线最小实现→基线评测→修复缺口→回归→记录真实取舍。

## 数据和责任合同

先形成独立可运行小闭环，不在第一步重建全部平台；新增代码与原参考快照分离。

## E16 设计能揭穿缺陷的样例

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

测试不能只是把当前输出抄成期望值，必须依据业务合同定义应有行为。

**代码入口**

`docs/EXISTING_CODE_SPEC.md`。路径相对于agent-eval-project；这是参考源文件。先读合同与分支，再看实现细节。

**按顺序完成**

1. 建5类场景：纯外部失败、内部参数错误、失败后真正恢复、同任务重复报错、证据不足。
2. 为每条标任务ID、节点、预期内部责任、应引用的证据和是否允许弃权；给一个反例而不是只测正常路径。
3. 给关键指标定义分母：模块正确、内部误报、证据有效、弃权与覆盖率，规划人工复核。

**失败场景与边界**

把全部样例标unknown可以降低误报，却没有实用覆盖率；要同时报告。

**本任务验收产物**

完成至少10条候选样例与标注说明；这是未执行评测集草案，不宣传准确率。

**面试追问**

如何评价归因系统好坏？

**回答必须包含的要点**

同时看结论、证据、内部责任误报和覆盖率，并检查失败类型而不只看总分。

## E17 规划自己的第一个可运行增量

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

旧脚本有硬编码、导入副作用和多种合同，先包成稳定离线闭环更利于理解与验证。

**代码入口**

`README.md`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 为新的src/tests定义输入适配、规范模型、失败检测、归因结果与报告的模块边界。
2. 写最小Spec：一份合成JSONL输入→确定性分析→JSON/Markdown报告，禁止把源快照当直接生产入口。
3. 优先安排node ID有效性、严格内部门禁和任务去重等明确缺口，每项关联E16反例；线上模型作为以后独立适配层。

**失败场景与边界**

仅搬文件改名不是算法或工程改进；要有明确合同、故障样例和验证。

**本任务验收产物**

交付可实施的增量Spec：文件/类/函数、输入输出、3～5个验收场景、运行方式和限制。

**面试追问**

你在原项目基础上加了什么？

**回答必须包含的要点**

完成后按实际的合同统一、校验、评测或可靠性增量回答，避免把参考原功能写成本人首创。

## E18 讲清真正的一步一步

- [ ] 能解释业务问题
- [ ] 能跟踪关键代码与数据
- [ ] 能给出失败样例和验收结果

**为何需要这一步**

教学重建帮助理解，但不能替代自己实施的真实开发节点。

**代码入口**

`HANDOFF.md`。仓库根为job-agent-v3；方法名可在文件内搜索，先读合同与分支，再看实现细节。

**按顺序完成**

1. 用“参考基线→复现→发现缺口→新设计→验证与取舍”形成90秒项目介绍。
2. 为每个真实增量保留Spec、Issue/ADR、代码、样例、结果和失败记录；从现在形成真实Git历史。
3. 对Redis/PG/async基础按被测平台和自己的实现分别说明，未亲自部署的模块如实注明。

**失败场景与边界**

不能倒签提交或捏造曾经遇到的生产事故；假设故障用于验证时明确标注。

**本任务验收产物**

产出贡献边界表、90秒介绍及5轮追问答案；任何数字都能回到真实实验。

**面试追问**

这不是你写的项目，你为什么了解？

**回答必须包含的要点**

如实说参考来源和学习/复现过程，再以自己能够验证的机制与真实改进证明能力。

## 本章结束检查

合上代码，用一个例子讲述本章链路。遇到无法解释的节点再回到对应文件；不需要抄写全部实现。把仍未验证的结论写进学习记录，不靠猜测补齐。

验证练习先用合成材料和离线依赖。本章列出的是学习操作和预期产物，并未声称这些实验已经执行。

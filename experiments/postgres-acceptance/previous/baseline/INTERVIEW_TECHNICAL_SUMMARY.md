# 可以真实讲述的工程总结

“已有 Agent 平台能够运行、评分和保存 Trace，但第一轮语义归因审核把字段不相等当成任务违规，还只检查结果能否找到一个调用，没有检查该调用是否有冲突结果。我在独立 Shadow 里修复这两个边界：参数违规只接受用户明确闭集约束的违反，工具结果按 scope 和调用身份双向校验，重复事件去重，冲突无法确认就保留未知。没有改原平台评分或业务链。”

## 技术难点与选型

1. **字段差异与业务语义不同。** 年份不相等可能是同比或基期需求。模型解释用户意图不是独立证据。本轮选择限制自动支持范围，牺牲部分覆盖来避免错误支持；没有声称通用自然语言理解已实现。
2. **身份配对不是简单 join。** 一个 Call 可能有重复、冲突或重放结果；同 ID 的两个 Call 又可能来自不同尝试。分组检查方向、来源、scope、顺序和内容一致性，比“取最新”更可靠，但依赖上游身份质量。
3. **相同重复与真实新执行分开。** 同一逻辑结果的重复可通过任一原 ID 引用，新 toolCallId 的重试保留新旧事件；复用 Call 身份无法确认时不猜测。
4. **LLM 是否必要必须有合理规则 Baseline。** 旧六次模型候选里的字段差异都可用简单 JSON 比较算出。新审核能支持的四条观察增强规则均可发现，所以旧 4/4 覆盖不证明 LLM 独有价值。
5. **引用、真值、支持、根因要分别评估。** 引用组 91/91 原文存在却仍接受 20 个不受支持声明。正确的局部观察也不等于内部根因。
6. **评测流程本身需要审计。** 算法先冻结，数据和人工复核再冻结，正式运行后不改候选。单作者流程分离仍不等于独立盲测。人工语义可支持但机器未实现的结论必须算真实 Gap，而不是藏到合同之外。

## 真实结果和反例

48 个单作者合成场景中，同一份人工候选旧审核 False Support 8、新审核0；两者 False Gap都8。增强规则有22个有效观察，覆盖19/28正例；固定人工候选经审核保留17个，覆盖14/28。新的真实模型实验没有运行，不能把这些说成 DeepSeek 的真实准确率。

旧六次真实输出离线复核：新审核支持4条，增强规则同样支持4条，LLM-only增量0。这个结果局限于已见简单数据，不代表复杂场景永远不需要LLM。

回归新18、原Python36、TS71通过，旧Shadow原版15可复现；但旧15测试换新版有3项不适配，因原来无闭集也默认支持A。保留了未改断言和失败日志，没有宣称完全兼容。

八条剩余Gap包括中文新约束、自然语言回答、字段同义、单位和否定。它们是下一步待解决的证据提取与审核问题；本轮没有靠增加模型调用或删测试掩盖它们。由于真实LLM增量、独立Gold和成本收益不足，最终不推广。

## 源码学习顺序

- `previous/shadow/semantic_review.py`：先复现旧的两个缺陷，理解为何局部看起来合理仍会误支持。
- `candidate/facts.py`：allowed_values / result_index；画出一对多 Call→Result 图和闭集约束。
- `candidate/review.py`：看支持范围收紧、短摘录同字段上下文、冲突拒绝及因果边界。
- `candidate/baseline.py`：学习在调用LLM之前用通用规则验证能覆盖什么。
- `test_round2.py`：同比、基期、身份重试、ID重命名和顺序变形；避免只针对两个Case写特判。
- `data/build_cases.py`、LABEL_REVIEW、LABEL_ADDENDUM：数据与Oracle如何独立于审核输出定义，为什么原始版本应保留。
- `evaluate.py`：案例与声明分母、Unknown、NA、FalseSupport与FalseGap。
- `results/analysis.json`、`PROMOTION_DECISION.md`：从真实反例做上线判断，不以代码量或局部100%下结论。

可以讲“可追溯的保守语义观察原型和质量评估”，不能讲“已验证生产级自动根因定位”或“LLM可靠超过非LLM规则”。

# 两个审核缺陷：根因、修复与证据

## A：不相等不是违反任务

原版把 user.year 与 call.arguments.year 的不同直接解释为参数错误。year 可能只是关注年份；同比、多年份与基期查询均可能合法。原版还无法处理明确业务允许值集合。

新支持条件限定为：调用前最近一轮 user.content 含用户明确提供的 `parameterConstraints`，例如：

```json
{"task":"只允许比较2025与2024","parameterConstraints":{"year":{"allowed":[2025,2024],"closed":true}}}
```

字段值必须不属于该封闭集合，候选 expected 必须属于集合，actual 必须等于所引调用参数；用户字段和调用参数均必须引用。支持的是“参数超出明确闭集”，不再把 expected 说成唯一合法年份。集合内查询不会被支持为错误。

该字段不是 LLM 解析出的可信意图：当前仅认可原始 user 节点直接携带的结构化合同，不信工具或模型解释。真实 UI/Trace 通常没有此字段，因此会保守 Needs Review；本轮没有给真实用户任务自动生成它。纯自然语言、year 标量、open set、缺少约束与新一轮未明确约束均不自动继承、猜测或接受。多轮比较只取 Call 之前最新 user，后续要求不溯及既有调用。

这是能力范围收紧，不是通用用户意图理解。若结构化合同与自然语言相互矛盾，当前协议假定显式闭集是用户认可的权威输入；生产应用必须先解决合同采集与一致性，不能直接套用到任意抽取结果。

## B：反向唯一配对不保证结果可信

原 paired(result) 只数前面有几个匹配 Call。同一次 Call 的两个矛盾结果都各自能找到这个 Call，随后 max(sequence) 任意选一个。

新 `result_index` 以执行 scope + toolCallId + 来源 + 工具名建立双向分组，要求：身份非空、来源已知、一个逻辑 Call、Result 在 Call 之后。组内结果内容/错误状态若不同，标记 conflicting_results_for_call；同实体或无法确定实体的歧义结果阻止相关答案/旧值结论。不同已知实体的歧义不为当前实体提供证据。

- 完全相同及仅 JSON 空白不同的重复 Result：视为同一逻辑结果，允许引用任一原始 ID，不伪造引用，也不算两个独立旧值证据。
- 新 toolCallId 再执行：独立尝试，可按可见顺序比较新旧结果。
- 多个 Call 复用同一身份：即使参数相同也无法确认是重复事件还是不同尝试，保持 ambiguous_or_missing_call；没有伪造 replayOf 语义。
- 同身份成功与失败、不同状态、跨 scope、缺失 Call、并行身份碰撞：拒绝支持，保留具体原因。

Scope 缺省时继承已经绑定的根 scope；若原提取丢失了真实线程身份，本审核不能凭空恢复。当前没有为生产 span 完整性背书。

## 文件与测试

改动仅为 candidate/review.py（旧版局部派生）、facts.py、新 baseline 与测试。原版在 previous/shadow/semantic_review.py；前后可直接比较，无平台恢复操作。

`test_round2.py` 14 项覆盖：披露两例、单年份、同比、多年份、基期、集合外、不明确要求、多轮修改、完全相同/空白重复、成功失败冲突、Call 冲突、跨线程、新身份重试、恢复、不伪造 stale、ID 重命名/顺序移动/序号平移、严格类型、漏引约束与不修改输入。`test_metrics.py` 另 4 项验证 NA、真实引用不等于真命题、未知根因与非法 Mock。

开发阶段曾有一项类型测试失败，根因是测试构造器仍把 expected 固定为 2025；修为传入集合首值后 14 项通过。原失败日志 dev-tests.log 保留，不是修改算法绕过断言。

## 正式冻结集结果

48 例、同一份人工候选：原审核接受 25 条，其中 8 条不受支持（4 错误、4 不可判）；新版接受 17 条，均有支持，False Support 8→0。False Gap 原/新均为 8，没有在本集合新增误拒。被移除的八条为 case-03/04/05/06/08/12/23/43；引用和原因见结果。

这不是泛化证明，也不是模型质量成绩。相同结果重复和新调用重试得到正确支持；自然语言/字段映射/单位的八个正确命题依旧被拒，详见失败报告。旧模型保存输出中的两个 A 因没有闭集约束从接受变为未知，明确记录，不把这一兼容变化隐藏掉。

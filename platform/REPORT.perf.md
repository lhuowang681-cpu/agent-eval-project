## 1. 单请求端到端延迟

每组 10 次串行，Mock LLM 首 token 0ms、输出速率不限（把 LLM 变成常量，测的是框架自身开销）。

| 场景 | 步数 | P50 | P90 | P95 | P99 | 成功率 |
| --- | --- | --- | --- | --- | --- | --- |
| 纯文本（无工具） | 1 | **398ms** | 432ms | 474ms | 474ms | 10/10 |
| 单工具 | 3 | **728ms** | 764ms | 765ms | 765ms | 10/10 |
| 三工具并行 | 3 | **772ms** | 980ms | 1032ms | 1032ms | 10/10 |

**读数**

- 纯文本单步基线约 **400ms**。LLM 是零延迟的 Mock，所以这 400ms 全部是框架开销：tRPC 往返、消息落库、operation 创建、上下文工程、状态存取、事件发布、SSE。
- 从 1 步到 3 步增加约 **330ms**，即**每增加一轮（LLM + 工具）约 165ms**。
- **三工具并行只比单工具慢 44ms（P50）** —— 三个工具确实是并行执行的，不是串行三次。这与 F4.2 的步数断言（都是 3 步）互相印证。

## 2. 各步耗时分布

样本：最近 20 分钟内 50 次运行、140 个步骤。

| 步骤类型 | n | P50 | P90 | P95 | P99 | max |
| --- | --- | --- | --- | --- | --- | --- |
| `call_llm` | 120 | 39ms | 271ms | 564ms | 1094ms | 1097ms |
| `call_tool` | 20 | 47ms | 91ms | 93ms | 100ms | 100ms |

| | 绝对耗时 | 占步骤耗时 |
| --- | --- | --- |
| `call_llm` 步骤 | 12,893 ms | 93.3% |
| `call_tool` 步骤 | 920 ms | 6.7% |

`call_llm` 的 P99（1094ms）远高于 P50（39ms），是因为样本里混入了档位扫描的 1000ms 档 —— 不是抖动。

### ⚠️ 一处口径问题，如实记录

快照的 `startedAt` / `completedAt` **不覆盖完整请求**：

```
快照 wall 合计    11,879 ms
步骤耗时合计      13,813 ms
差值              -1,934 ms   ← 负数
```

各步 `executionTimeMs` 之和**超过**快照自身的 wall。同时快照 wall 的 P50（125ms）远小于 bench 侧实测的 E2E P50（398ms）。

结论：**`agent-tracing` 快照的时间跨度不能当作端到端耗时使用**。因此本报告不给出「框架余量 = wall − 步骤和」这类拆解 —— 那会得到负值。端到端一律以 `bench/run-scenarios.ts` 的外部计时为准。这本身是 agent-tracing 的一个可用性局限，值得反馈。

## 3. LLM 耗时 → 端到端的传导

固定其它条件，只调 Mock LLM 的首 token 延迟，每档 5 次。

| 首 token 延迟 | E2E P50 实测 | 线性预期 | 偏差 |
| --- | --- | --- | --- |
| 0ms | 452ms | 452ms | 0ms |
| 200ms | 642ms | 652ms | **−10ms** |
| 500ms | 933ms | 952ms | **−19ms** |
| 1000ms | 1435ms | 1452ms | **−17ms** |

**传导系数约 1.0，偏差全部在 ±20ms 内。**

含义：LLM 侧每增加 1ms，端到端就增加约 1ms —— 框架**没有**放大 LLM 延迟，也没有通过并行/预取掩盖它。可以据此外推真实 provider 下的表现：

```
真实 E2E ≈ 框架基线（约 400ms / 步） + 真实 LLM 耗时 × LLM 调用次数
```

例：一次含 2 次 LLM 调用、首 token 800ms 的对话 ≈ 400 + 330 + 800×2 ≈ **2.3 秒**。

## 4. 成本结构参数

这些与 provider 无关，可直接外推。

| 参数 | P50 | 均值 | max |
| --- | --- | --- | --- |
| 每次对话步数 | 2 | 2.8 | 4 |
| 每次对话 LLM 调用数 | 2 | 2.4 | 3 |
| 每次对话工具调用数 | 0 | 0.4 | 1 |
| 每次对话总 tokens | 65 | 140 | 383 |
| 每次 LLM 调用 tokens | 33 | 53 | — |

按场景：

| 场景 | LLM 调用 | 工具调用 |
| --- | --- | --- |
| 纯文本 | 1 | 0 |
| 单工具 | 2 | 1 |
| 三工具并行 | 2 | 3 |

**输入/输出 token 比 = 14.0** —— 每产出 1 个 token 要送进 14 个 token。这是上下文工程的成本代价，也是最值得优化的杠杆点。

### 上下文随步数放大

| 步骤 | n | 输入 tokens P50 | 均值 |
| --- | --- | --- | --- |
| step 0 | 50 | 36 | 36 |
| step 2 | 20 | 136 | 211 |

**从 step 0 到 step 2，输入 token 放大 3.78×。**

这是在极短对话（Mock 回复很短）下测得的。真实对话中每一步都会把完整历史重新送进去，放大倍数会显著更高 —— 这正是附录 A 里「每步全量序列化 + 上下文流水线每步全量重跑」两条风险的成本侧体现。

### 成本推算方法（未经校准）

```
单次对话成本 ≈ Σ(每次 LLM 调用的输入 tokens × 输入单价 + 输出 tokens × 输出单价)
             ≈ LLM 调用次数 × 每次调用 tokens × 加权单价
```

代入实测结构参数（2.4 次调用、每次 53 tokens），**在 Mock 的短对话下**每次对话约 130 tokens。真实场景需按真实上下文长度重算 —— 关键变量是上下文长度，不是调用次数。

## 5. 与压缩阈值相关的一处修正

L1 测试暴露出 `DEFAULT_THRESHOLD_RATIO = 0.65`，而既有测试里写死 `64_000` 并注释 `// 128k * 0.5`（详见 [05-functional-report.md §1.1](docs/analysis/05-functional-report.md)）。

**上下文压缩的实际触发点是窗口的 65%，不是 50%** —— 128k 窗口下是 **83,200** tokens。任何关于「压缩多久触发一次」的估算都必须按 65% 算，否则会低估门槛、高估压缩频率。

## 6. 状态写放大 —— O(N²) 已实测证实

> 2026-08-07 补测。这原本在「待将来补测清单」里（认为需要 Redis），实际**不需要** ——
> 写放大是**序列化字节量**的性质，与字节落到哪里无关。因此可在无 Redis 环境下直接测量，
> 结论同样适用于 Redis `SETEX` 路径（`AgentStateManager.ts:55`）。

**方法**：`growth` 场景驱动 12 轮工具调用 + 收尾（共 26 步），从 `.agent-tracing` 快照的
`messagesBaseline` + `messagesDelta` 精确重建每步的 messages 数组并序列化计字节。
测量脚本 `bench/write-amplification.ts`。

### 实测

| step | 消息数 | 本步序列化字节 | 累计写入 |
| --- | --- | --- | --- |
| 0 | 2 | 1.4 KB | 1.4 KB |
| 5 | 7 | 4.3 KB | 17.0 KB |
| 10 | 12 | 8.2 KB | 50.2 KB |
| 15 | 17 | 11.1 KB | 99.8 KB |
| 20 | 22 | 15.0 KB | 167.0 KB |
| 25 | 26 | 16.6 KB | **248.3 KB** |

### 判定

| 指标 | 值 |
| --- | --- |
| 单步字节 首→末 | 1.4 KB → 16.6 KB（**12.1×**） |
| 单步增长斜率 | **0.61 KB/步**（近似常数 → 单步为 O(n)） |
| 累计写入 | 248.3 KB |
| 若单步恒定的线性基准 | 35.8 KB |
| **放大倍数** | **6.9×** |
| 二次模型拟合误差 | **5.8%** |

单步字节随步数**线性增长**，累计写入因此是**二次的** —— 二次模型以 5.8% 的误差拟合实测值，
**O(N²) 的判断成立**。

### 外推

| 对话步数 | 单步序列化 | 累计写入 |
| --- | --- | --- |
| 20 | 13.6 KB | 143 KB |
| 50 | 31.8 KB | 815 KB |
| 100 | 62.3 KB | **3.1 MB** |
| 200 | 123.2 KB | **12.1 MB** |

一次 200 步的长对话，仅**状态持久化**一项就要写 12 MB，且其中绝大部分是同一批消息被反复重写。
生产 Redis 模式下这些字节要经网络往返；本地模式下则是同步 `JSON.stringify` 阻塞事件循环
（`runtime.ts:86` 的 `structuredClone` 同理）。

### 边界

- 以上是 **messages 数组**的字节。完整 state 还含 `toolManifestMap` / `operationToolSet` /
  `usage` / `cost` 等，每次运行近似恒定，构成一个**附加基底**，不改变 O(N²) 的结论
- 测的是**字节量**，不是 Redis 的实际吞吐/延迟 —— 后者仍需真 Redis 验证
- 本次样本的每轮内容较短（Mock 回复约 0.6 KB）。真实对话中单条消息大得多，斜率会显著更陡

### 结论

这是本次分析中**成本收益比最高的优化点**：改为状态差量持久化（只写 delta，而非每步全量），
在 100 步对话上可把写入量从 3.1 MB 降到约 60 KB 量级。

## 7. 结论

**可以下的结论**

1. 框架单步开销约 **400ms**，每增加一轮约 **165ms**（Mock LLM、PGlite 环境下）
2. 工具批量调用**确实并行**，三工具仅比单工具多 44ms
3. LLM 延迟**线性传导**到端到端，系数约 1.0，框架不放大也不掩盖
4. 输入/输出 token 比 **14:1**，上下文是主要成本来源
5. 上下文在 2 步内就放大 **3.78×**
6. **状态写放大是 O(N²)** —— 26 步放大 6.9×，二次拟合误差 5.8%，100 步外推累计写入 3.1 MB（§6）

**2026-08-08 补测后可以补上的结论**（环境：真 PG + 真 Redis + queue 模式）

7. **并发下错误率全档 0%**（1→50），连接池零告警
8. **RPS 在 5 并发后即平台化**（~43），此后延迟随并发线性上升而吞吐不增 ——
   说明瓶颈在**串行化处理**，不在连接数
9. **步锁在 queue 模式下确实生效**：并发同一步 → 恰好 1×200 + 1×429 且 `Retry-After: 37`

  **绝对值不可直接外推到生产**
- token 成本的绝对金额
- Redis 侧的实际吞吐/延迟（字节量已测，见 §6；真实 Redis 的网络与序列化行为仍未单独测量）

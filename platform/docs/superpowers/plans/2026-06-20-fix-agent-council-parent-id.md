# Fix AgentCouncil Parent ID Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prevent group chat from sending a virtual `agentCouncil-*` display message ID as `newUserMessage.parentId` after the last visible message is an AgentCouncil card.

**Architecture:** Keep the database parent chain based on persisted `messages.id` values. Fix the display-message selectors so virtual container messages resolve to the deepest real message ID before `sendMessage` builds the request payload. Do not relax the database foreign key and do not persist AgentCouncil virtual IDs.

**Tech Stack:** TypeScript, Zustand selectors, `@lobechat/types`, Vitest, Chrome/CDP manual verification.

---

## Summary

The reproduced failure is caused by the frontend sending this virtual display ID as `parentId`:

```text
agentCouncil-msg_oMnKgYqTTnM3sl-msg_277NLk0iwGzW8f-msg_m6PJn5LcvOXSrg
```

That ID is generated by `packages/conversation-flow/src/transformation/FlatListBuilder.ts` for UI grouping only. It does not exist in `messages.id`, so `aiChat.sendMessageInServer` fails when inserting the new user message with a foreign-keyed `parent_id`.

The primary fix is to make `findLastMessageIdRecursive` understand `agentCouncil.members` and return the last member's real tail message ID. The same logic exists in two selector files and must be kept consistent.

- [ ] **Step 2: Update `findLastMessageIdRecursive`**

Replace the current function body with this logic:

```ts
const findLastMessageIdRecursive = (node: UIChatMessage | undefined): string | undefined => {
  if (!node) return undefined;

  if (isAgentCouncilDisplayMessage(node)) {
    const lastMember = node.members?.at(-1);
    const lastMemberId = findLastMessageIdRecursive(lastMember);

    return lastMemberId ?? node.extra?.parentMessageId;
  }

  if (node.children && node.children.length > 0) {
    const lastChild = node.children.at(-1);
    return findLastBlockId(lastChild);
  }

  if (node.tools && node.tools.length > 0) {
    const lastTool = node.tools.at(-1);
    return lastTool?.result_msg_id;
  }

  if (node.role === 'compressedGroup' && 'lastMessageId' in node) {
    return (node as { lastMessageId?: string }).lastMessageId;
  }

  return node.id;
};
```

Decision: do not fall back to `node.id` for `agentCouncil`, because `node.id` is the virtual `agentCouncil-*` ID that caused the production failure. If `members` is empty and `extra.parentMessageId` is unavailable, return `undefined` so the caller does not send an invalid virtual parent.

## Assumptions

- `agentCouncil-*` IDs are display-only and must never be used as persisted `messages.parent_id`.
- `agentCouncil.extra.parentMessageId` is a real persisted message ID generated from `FlatListBuilder.createAgentCouncilMessageFromChildIds`.
- The correct continuation parent after an AgentCouncil card is the tail of the last council member, recursively resolving assistant groups and tool result messages.
- The database foreign key is correct and should remain strict.
- Server-side validation for virtual IDs can be added later as defense-in-depth, but it is not the primary fix because the frontend already has enough display-tree information to send the correct parent ID.

## Optional hardening after the primary fix

Add a defensive guard in the server action that rejects any incoming `parentId` starting with known virtual prefixes such as `agentCouncil-` before the insert. Return a clear client error instead of leaking a raw DB insert failure. This is intentionally secondary; it should not replace the selector fix.
